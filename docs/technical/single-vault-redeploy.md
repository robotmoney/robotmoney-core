# Single-vault redeploy into a live deployment

## 1. Purpose, scope and owner decision

This procedure describes one rmPROTO replacement in Deploy 2 on Base (8453). The ProtocolAssetVault sell-floor fix (1778) changed the vault sell floor to price `sellAmount - 1`; the old rmPROTO has old bytecode. It is a plain deployment, not a proxy, and the deploy script uses `new ProtocolAssetVault` ([DeployProtocolAssetVault.s.sol:63-78](../../contracts/script/DeployProtocolAssetVault.s.sol); [redeem-gas-1482.md:111-119](redeem-gas-1482.md)).

The owner approved an experiment on 2026-10-13, tracked by single-vault redeploy issue (1796) (phase issue (1679)) and devops issue (72). This experiment is an explicit exception to the owner's one-deployment-scheme rule for Deploy 2 only. It does not establish a general live-deployment migration scheme. Before the final deployment uses this path, the owner must decide yes or no whether the exception becomes an approved release procedure, and whether the one-scheme rule remains in force for all other deployments.

This page specifies a new closed vault, role handover, registry registration, eligibility and default-weight migration, retiring the old vault, verification, and a 1 USDC router round trip. It does not move old shares. The contracts have no share migration in this procedure; holders exit from the old vault.

## 4. Ordered procedure

Every governance call is scheduled by the Safe and executed through the timelock. Use the on-chain `getMinDelay()` read for each scheduled operation. Deploy 2's recorded 900-second rehearsal setting is historical and not proof of today's delay (`devops/docs/plans/deploy-correctness.md:102-110`). A public executor may execute a ready operation; the Safe holds proposer and canceller roles ([DeployTimelock.s.sol:72-89](../../contracts/script/DeployTimelock.s.sol)).

|---|---|---|---|

## 5. Interleaving risk

The router uses the effective vector (voted vector when active, otherwise defaults) and computes availability from registry Active status plus eligibility ([PortfolioRouter.sol:647-680, 745-754, 963-1003](../../contracts/PortfolioRouter.sol)). `previewDeposit` and `deposit` share the same registry-status/eligibility availability and renormalization calculation. An unavailable leg is skipped, and the remaining eligible weights are renormalized to 100%; a per-vault cap can still make the entire transaction revert ([PortfolioRouter.sol:688-739](../../contracts/PortfolioRouter.sol)). The router does not include the vault-local `depositsPaused` flag in `_isDepositable` ([PortfolioRouter.sol:741-754](../../contracts/PortfolioRouter.sol)). Zero-amount legs are skipped, as required by zero-leg skip fix (1747) ([PortfolioRouter.sol:1017-1030, 1064-1069](../../contracts/PortfolioRouter.sol)).

| Between actions | Router deposit / preview | Redeem | Receipt apply, pause, keeper |
|---|---|---|---|
| Deploy and role handover | New vault is not eligible, so old split is unchanged. After separate registration it is Active, but ineligible. Preview excludes it. | Old and other registered positions remain redeemable. | Receipt apply can change effective weights if governance still permits it; pause can close old or other vault direct deposits. A keeper action does not alter registry eligibility. Do not start while a conflicting receipt application or pause/unpause is queued. |
| After role handover, before the cutover batch | Old rmPROTO remains the only rmPROTO router leg. New vault stays closed and ineligible. | Old exits continue. | No adapter keeper has authority to change router eligibility. The keeper price recorder call may update a price record, not router state. |
| Between separate migration transactions (unsafe) | If only the old-to-ineligible call executes, old is out of the vector and no rmPROTO leg exists. Remaining eligible legs renormalize to 100%; preview reports that split and router deposits follow it. Old remains Active and direct deposits can still occur until retirement. The atomic final batch eliminates this interval. | Existing holders can redeem old shares. Router `redeemFor` accepts caller-named registered vaults independent of current weights/status ([PortfolioRouter.sol:850-950](../../contracts/PortfolioRouter.sol)). | A receipt apply might replace the router vector with voted weights; check `votedWeightsActive` and effective vector after the migration. A pause-all can pause deposits while leaving redeems open. Keeper calls do not move user shares. |
| Between separate cutover calls (unsafe) | If the new vault is Active and eligible while its local `depositsPaused` flag is true, `_isDepositable` still treats it as available. `previewDeposit` can quote it, then `deposit` calls the vault and reverts; the router transaction reverts as a whole. If old has already been retired, other legs are not automatically renormalized around the local pause. paused-leg decision Q3 (1705) documents this unresolved behavior ([PortfolioRouter.sol:741-754, 1017-1035](../../contracts/PortfolioRouter.sol); [BasketVault.sol:1254-1268](../../contracts/vaults/BasketVault.sol)). The atomic cutover batch removes this visible interval. | Both old and new registered vault shares remain redeemable; old positions exit from old. | A receipt apply can replace the effective vector, so require no voted vector and block concurrent receipt apply. A pause after scheduling the cutover makes its queued `unpauseDeposits()` stale; cancel the batch before any open executor runs it. A keeper price recorder can change price observations and make the new vault deposit guard fail, reverting the whole router transaction. A keeper rebalance must be checked for asset effects; it does not change registry eligibility. |
| After opening new | Intended four-way split remains 8550/525/575/350, unless a voted vector is active. Zero-leg skip means any zero bps leg is not called; with Deploy 2's positive weights all four should get a nonzero allocation for 1 USDC, subject to rounding and availability. | Old withdrawals stay available; new shares redeem under new bytecode. | Pause after opening blocks new deposits on that vault, not redemptions. A queued unpause must not execute after pause-all; the existing govern tool tracks this ordering but this new operation needs equivalent handling ([govern.ts:31-39, 525-537](../../publish-contracts/src/govern.ts)). |

**Safe order:** deploy closed without registry writes; finish role handover; register through the Safe/timelock; schedule one final batch that opens the new vault, removes old eligibility, adds new eligibility with the full vector, and retires old. Do not retire old before it is ineligible: `retire` reverts. Separate eligibility transactions expose a three-leg normalized split; separate opening/migration transactions expose a paused-leg router revert ([VaultRegistry.sol:276-287, 389-455](../../contracts/VaultRegistry.sol); [PortfolioRouter.sol:710-754](../../contracts/PortfolioRouter.sol)).

## 6. Old vault and holder exit

Retirement changes registry status and invokes the vault's deposit halt. It does not burn shares, transfer assets, migrate holders, or remove the address from the registry list ([VaultRegistry.sol:266-287](../../contracts/VaultRegistry.sol)). Old vault withdrawals/redemptions must never be frozen; `redeemInKind` has no pause, shutdown, retired, or role gate and pays idle USDC plus each active basket token pro rata ([BasketVault.sol:705-720](../../contracts/vaults/BasketVault.sol)). The standard `redeem` path remains governed by its normal pricing and liquidity conditions. Router `redeemFor` uses an explicit registered-vault list, so a retired or reweighted-out position remains reachable ([PortfolioRouter.sol:850-950](../../contracts/PortfolioRouter.sol)).

A holder such as `0x2B918144e4Aa55450a542743e7d52CB7eE5a02b6` keeps the old rmPROTO shares. They may call `redeem` when its normal conditions succeed, or approve a caller and use `redeemInKind(shares, receiver, owner)` for a token-basket exit if the USDC swap path cannot price or fill. Do not assume those shares can move to the new vault. They represent shares in a different contract with a different supply and asset accounting.

## 7. Verifier and evidence changes

The current verifier binds manifests to a fixed four-vault sheet and checks code, roles, configs, and effective/default router vectors ([verify/index.ts:79-110, 148-149, 203-212, 248-274](../../publish-contracts/src/verify/index.ts)). A redeploy verifier needs an explicit migration record and must check:

- New address has code; code hash matches the tagged artifact with constructor immutables/links handled as the current verifier does. Retired-address bytecode matches the pre-migration record.
- New vault's USDC, SwapRouter02, caps, fee, fee recipient, asset list, pools, fees, oracle/deviation/slippage config, paused flag, and role holders match the approved old-vault configuration.
- Deployer has no role. Timelock holds admin; approved emergency responder holds emergency role. Enumerate every role holder, not only expected singleton holders. The role-holder enumeration fix (1668) requires enumerating role holders; the current verifier uses role-count checks and log-enumerated scans ([verify/index.ts:123-130, 553-578](../../publish-contracts/src/verify/index.ts)); extend those scans for the redeployed vault.
- Old vault is registered, Retired, router-ineligible, and still permits a read-only redeem preview / `redeemInKind` call simulation.
- New vault is registered Active and eligible; eligible count and default vector length equal four.
- `votedWeightsActive == false`; default and effective vectors both identify the new rmPROTO address at 525 bps; the other weights are 8550/575/350.
- All four vault pause/retired states, role enumeration, caps, and bindings are recorded before and after. The test deposit and redemption amounts and transaction hashes are tied to the new address.

The run manifest/evidence must record tag, SHA, chain ID, old/new addresses, both code hashes, constructor and library config, pool bindings, all role holders, pause flags, registry status/eligibility, router default/effective/voted state, Safe operation IDs, scheduled/ready/executed/cancelled transactions, and test balances/results. Evidence check must reject a missing cutover step, an unexpected role holder, a stale old address in the effective vector, active voted weights, or a mismatch between transaction and manifest. Existing manifest schemas do not describe a second vault under one logical rmPROTO key; schema design is unknown and must be decided before implementation.

## 9. Failure modes and rollback

| Failure point | Result and response |
|---|---|
| Deploy fails | No new address is committed if the transaction reverts. If deployment succeeds but later script steps fail, inspect registry and manifest; the contract may exist. Keep it paused and do not guess at the address. Retry must not duplicate-register. |
| Role handover fails | New vault remains closed. Complete or cancel the queued Safe operation. Keep deployer role until the timelock role is confirmed; never leave the vault with no admin. |
| Registration fails | New vault remains closed. If already registered by deploy script, treat an attempted second registration as an error and read back state. `AlreadyRegistered` reverts duplicate registration ([VaultRegistry.sol:235-249](../../contracts/VaultRegistry.sol)). |
| Migration fails | Transaction is atomic; eligibility and defaults do not partially persist ([VaultRegistry.sol:420-455](../../contracts/VaultRegistry.sol)). Old remains eligible under the prior vector. Fix calldata/config and reschedule. |
| Retirement fails | Old remains unretired if hook failure reverts. Check old eligibility/status and retry only after migration confirms it is ineligible. |
| Opening fails | New remains closed; old is retired and new is eligible. Router skips new and renormalizes over available legs. Pause and stop deposits while restoring an approved open path. |
| Verifier or 1 USDC test fails | Call `pauseDeposits()` on the new vault with the emergency key if available; withdrawals remain open. Use Safe/timelock for admin corrections. Do not reopen until checks pass. |
| Half-applied sequence | Read actual state, not the manifest alone. If a migration call landed outside the intended batch, old may be out of the vector while still directly depositable. If retirement landed while new remains locally paused and eligible, router deposits that include new can revert instead of renormalizing. Keep new closed, stop new user deposits operationally, and resume only from the first verified incomplete operation. |

An abort before migration leaves old as the routed rmPROTO; the unused new vault can remain registered but paused/ineligible. After migration, Safe may schedule the inverse `migrateEligibility(new,false,[rmUSDC,old,rmAGENT,rmRWA],[8550,525,575,350])` only if old remains Active. `reactivate(old)` is required after retirement, and must precede making old eligible because weight validation requires Active. Every repair call uses the actual timelock delay ([VaultRegistry.sol:290-300, 432-455](../../contracts/VaultRegistry.sol)). The Safe can cancel a pending operation through the timelock's `cancel(operationId)`; any open executor can execute a ready operation, so cancel must land before execution ([DeployTimelock.s.sol:72-88](../../contracts/script/DeployTimelock.s.sol)).

What cannot be undone: deployment cannot be erased; registration is append-only; the old and new addresses and their shares remain distinct. A holder who redeems old shares has burned them. A completed external swap, transfer, or deposit cannot be reversed by registry state. The old vault cannot be made equivalent to the new bytecode. Retired state can be reversed by governance while contract hooks allow it, but that is a new governed action, not transaction rollback.

## 11. Security review

The 2026-10-12 review is on branch `review/contracts-security-20261012`, with findings 1, 2, 5, and 8 relevant here ([security review](https://github.com/robotmoney/robotmoney-core/blob/review/contracts-security-20261012/docs/code-review/20261012-security-review.md)). It states that live production state and bytecode were not independently verified (review §Scope and disposition).

- **Finding 1, excluded adapter value:** ProtocolAssetVault is not the RobotMoneyVault adapter strategy reviewed in finding 1. The review's excluded-adapter behavior cannot be assumed to describe rmPROTO ([review, finding 1](https://github.com/robotmoney/robotmoney-core/blob/review/contracts-security-20261012/docs/code-review/20261012-security-review.md)). Still compare the exact new vault asset/pool set with the old and verify NAV before deposits.
- **Finding 2, duplicate adapter registration:** also concerns RobotMoneyVault `addAdapter`, not this ProtocolAssetVault deploy. Registration of the vault itself is separately duplicate-guarded by `_registered` ([VaultRegistry.sol:235-249](../../contracts/VaultRegistry.sol)). Verify the new vault appears once and has the expected assets.
- **Finding 5, force removal:** applies to emergency force-removal of RobotMoneyVault adapters. It is not the same as registry `retire(old)`. Retirement blocks deposits but leaves exits and old assets in place ([VaultRegistry.sol:266-287](../../contracts/VaultRegistry.sol); [BasketVault.sol:705-720](../../contracts/vaults/BasketVault.sol)). Never use force removal as a migration tool.
- **Finding 8, duplicate router vectors:** the router's shared weight setter validates lengths, eligibility, status, and sum, but the shown source does not reject duplicate addresses ([PortfolioRouter.sol:537-563](../../contracts/PortfolioRouter.sol); review finding 8). Construct the vector from the four distinct registered vaults and verifier-check uniqueness as a new defense.
- **Open-executor timelock:** anyone can execute a ready scheduled operation. The executor does not create operations or change calldata, but can choose execution timing ([DeployTimelock.s.sol:72-88](../../contracts/script/DeployTimelock.s.sol); review finding 1 discussion). The migration must therefore be safe under public timing: schedule only the intended operation, monitor ready operations, and cancel stale or superseded operations before they execute. Recheck state and operation IDs before every scheduling ceremony.
