## Point A1 — same-second `recordedAt` is an intentional, fail-safe liveness cap

VERDICT: **remains advisory** (accepted design property; not promoted to a finding)

EVIDENCE:

- `contracts/ConsensusRecommendationReceipt.sol:167` — `uint64 recordedAt = uint64(block.timestamp);` (second granularity, one value for all txs in a block).
- `contracts/ConsensusRecommendationReceipt.sol:155-183` — `recordReceipt`: submitter-role gate (`:161`), non-zero id/digest/URI checks (`:162-164`), one-shot duplicate-id rejection (`:165`, `ReceiptAlreadyRecorded`), append-only push (`:168-180`). No rate limit, no per-block/per-second cap.
- `contracts/ConsensusRecommendationReceipt.sol:85,236-242` — `receiptId = keccak256("robotmoney:consensus-receipt-id:v1\n" + sessionId + "\n" + subjectId)`; §4.9.2 of architecture (`:820-822`) makes this "one receipt per session per subject". Two distinct receipts recorded in the same block therefore have distinct `receiptId`s; neither is a duplicate.
- `contracts/RouterGovernance.sol:86-93` — `lastAppliedRecordedAt`, appended in an unused slot, no setter, one-way monotonic.
- `contracts/RouterGovernance.sol:177-199`, specifically `:191-196` — strictly-greater guard `if (r.recordedAt <= last) revert ReceiptNotNewerThanApplied(...)`; cursor updated **before** `releaseReceipt` and `router.setWeights`; whole call atomic.
- `contracts/RouterGovernance.sol:121-123` — named error `ReceiptNotNewerThanApplied`.
- `contracts/test/RouterGovernanceApplyReceipt.t.sol:319-346` (`_scheduleBoth`), `:348-375` (`test_applyReceipt_outOfOrderOlderReverts`), `:377-395` (`test_applyReceipt_sameRecordedAtRefused`), `:397-411` (`test_applyReceipt_inOrderStillApplies`) — the exact behaviour is asserted with exact custom errors, not merely documented.
- `docs/architecture.md:857-865` — normative "Apply order (issue 1831)": `applyReceipt` reverts unless recorded strictly later; older apply reverts, older receipt stays unreleased, newer vector stays active. `:730-735` — "a receipt the Safe does not schedule changes nothing"; `:800-810` — release is discretionary and an unreleased receipt is an immutable record; `:909-910` — "a released receipt can be not applied". **No normative requirement that every recorded receipt be applicable.**
- `docs/technical/governance-decisions.md:93-101,209-239` — digest binding and apply semantics; no ordering requirement other than the monotonic guard.
- Production role holder (observed): `contracts/script/DeployConsensusRecommendationReceipt.s.sol:14-18` documents that the timelock alone grants `RECEIPT_SUBMITTER_ROLE`; `publish-contracts/src/submitter-register.ts:1-2,29-31` and `publish-contracts/src/cli.ts:124-125,159` show the grant target is a **Submitter Safe** (SafeL2 1.4.1, threshold ≥ 2), not an EOA/hot key. `publish-contracts/src/record-receipt.ts:1-16` shows the verb anchors **one** receipt per Safe execution. `contracts/test/RouterGovernanceApplyReceipt.t.sol:48,74-75,93-95` is the test stand-in (one submitter EOA, one receipt).
- Operator pre-check (observed): `publish-contracts/src/govern.ts:1799-1806,1828-1830` reads `lastAppliedRecordedAt` and refuses with USAGE **before** the Safe schedules a non-newer receipt.
- **Tests executed (this review, not inferred):** `FORGE_TEST_MIN_EXECUTED=1 bash .github/scripts/forge_test_require_executed.sh --match-contract RouterGovernanceApplyReceipt` → `Ran 12 tests ... 12 passed; 0 failed; 0 skipped`, `executed-test-guard: 12 forge test(s) passed (floor 1)`. `test_applyReceipt_sameRecordedAtRefused` and `test_applyReceipt_outOfOrderOlderReverts` were among the passes.

ANALYSIS:

- **Exact sequence.** Submitter records A and B in the same block (or two blocks the chain stamps with the same second): `recordReceipt(idA, ..., uriA)` then `recordReceipt(idB, ..., uriB)`; both get `recordedAt = T` and both succeed (`:165` only rejects a repeated id, and `idA != idB`). Safe schedules both applies; the open timelock executor may execute them in either order. If A executes first, `lastAppliedRecordedAt = T`; B then hits `r.recordedAt <= last` (`T <= T`) and reverts with `ReceiptNotNewerThanApplied`, leaving B unreleased and its vector unwritten. Symmetric if B executes first. A third receipt at `T+1` applied later only raises the cursor; A and B remain ≤ cursor and stay unapplicable. **At most one of the two can ever be applied** — the first-pass statement is exact.
- **Who can trigger.** Only a submitter holding `RECEIPT_SUBMITTER_ROLE` can create the collision, and only the Safe→timelock→`WEIGHT_SETTER_ROLE` path can apply either. The submitter is a Safe in production. There is no untrusted path: `recordReceipt` is role-gated (`:161`) and `applyReceipt` is role-gated (`:182`).
- **Can two receipts legitimately share a second?** Yes in principle — the contract has no per-block/per-second rate limit and `recordReceipt` accepts any distinct `receiptId`; a Safe *could* batch two `recordReceipt` calls in one `execTransaction`, and two separate Safe executions could land in one block. Operationally the `record-receipt` verb sends one receipt per invocation (evidence above), so the shape is unusual, not forbidden.
- **Is the loser permanently unapplicable?** As recorded, yes: `recordReceipt` refuses the same `receiptId` forever (`:165`), there is no update/delete path, and `lastAppliedRecordedAt` never decreases. It can only be superseded by recording a **new** receipt under a new `(session_id, subject_id)` → new `receiptId` in a later second and applying that. That is re-proposal, not re-recording.
- **Is there a normative "every recorded receipt must be applicable" requirement?** No. Architecture §4.8 says a receipt the Safe does not schedule changes nothing; §4.9.1 answer 3 says an unreleased receipt is an immutable public record that the dapp shows as "recorded, not released"; §4.9.3 says "a released receipt can be not applied". Applicability is deliberately discretionary. The monotonic guard is a *safety* property (newer vector wins), explicitly specified in issue 1831 and architecture §4.9 "Apply order".
- **Refutation as a finding.** Harm axis, if any, is availability/operational cost (one recorded recommendation cannot be applied), not release or assertion integrity: no wrong vector lands, no false assertion is made, and the affected receipt remains visible on-chain. Trigger is admin/operator-tier, not untrusted. It **fails safe** — the later apply reverts and nothing wrong is asserted (fails-unsafe is impossible here). The fails-safe downgrade is **not** cancelled: there is no documented-prohibition regression (the code implements architecture §4.9 exactly) and no operator/session corruption (no state survives the process beyond the intended immutable record). Per rubric that is `low` at most (availability + fails-safe + no escalator), realistically `info` once the documented design and the pre-schedule USAGE guard are credited. Diff-visibility is irrelevant at this band. Not merge-blocking.
- **Adversarial checks that did not survive:** an attacker reordering two ready applies is already handled (open executor + monotonic cursor; `test_applyReceipt_outOfOrderOlderReverts`); a stale vector cannot be applied after registry churn because `PortfolioRouter.setWeights` re-validates every leg at execution (`contracts/PortfolioRouter.sol:497-530,1414-1421`); a released-but-unapplied receipt is a documented burn, not this shape.

SEVERITY IF PROMOTED: **n/a**. If forced onto the rubric: `low` (availability/operational cost, admin/operator trigger, fails safe, no escalator) with `confidence: high`; `info` would also be defensible because no material harm axis beyond clarity is engaged. Either way below the merge-blocking line. Admin-only + fails-safe liveness caps at low/info, exactly as the assignment cautions.

RECOMMENDATION: Accept and document the property rather than change code: add one line to architecture §4.9 "Apply order" noting that equal `recordedAt` values make at most one of the tied receipts applicable and that the operator must re-record under a new `(session, subject)` if the other vector is still wanted. Retain the pre-schedule USAGE guard (`publish-contracts/src/govern.ts:1799-1806`) as the operator-visible control. No contract change; no new issue.

## Point A2 — `VaultRegistry` hook-call inconsistency requires a compromised timelock and produces no wrong value-bearing state

VERDICT: **remains advisory** (clarity/consistency only; not promoted to a finding)

EVIDENCE:

- `contracts/VaultRegistry.sol:239-254` — `registerVault`: `onlyRole(ADMIN_ROLE)`, rejects only `address(0)` (`:243`) and duplicates (`:244`). No `code.length`, interface or `asset()` check. Sets `Active` (`:251`).
- `contracts/VaultRegistry.sol:50-57` — `ADMIN_ROLE` is self-administered; sole holder is the deployer until `DeployTimelock` hands it to the `TimelockController`. All lifecycle writes are `onlyRole(ADMIN_ROLE)`.
- `contracts/VaultRegistry.sol:280-292` — `retire`: `NotRegistered` (`:281`), `RetireWhileRouterEligible` (`:288`), sets `Retired` (`:289`), then **unconditional** `IRetirableVault(vault).retire()` (`:290`).
- `contracts/VaultRegistry.sol:300-305` — `reactivate`: `NotRegistered` (`:301`), sets `Active` (`:302`), unconditional `IRetirableVault(vault).unretire()` (`:303`).
- `contracts/VaultRegistry.sol:331-364` — `setVaultStatus`: same `RetireWhileRouterEligible` guard (`:340-342`), but the hook is wrapped in `if (vault.code.length > 0)` (`:355-361`). NatSpec `:322-328` explicitly says a registered address lacking the hook "fails the call intentionally" — which the EOA branch does not do.
- Refuting value-flow guards in the router: `contracts/PortfolioRouter.sol:497-530` (`setWeights` → `_requireActiveAndEligible` every leg), `:545-611` (`setDefaultWeights`/`_setDefaultWeights`, length == `routerEligibleCount` + same guard), `:1248-1260` (deposit-time `Active` status recheck + `_requireRouterEligible`), `:1427-1445` (`_requireRouterEligible`: `vault.code.length == 0` → `VaultAssetUnreadable`, so an EOA can never enter a weight vector), `:1308-1335` (`getEffectiveWeights`).
- Registry interlocks unaffected by the code-check gap: `contracts/VaultRegistry.sol:381-408` (`setRouterEligible` + `StaleDefaultWeightsLength`), `:436-460` (`migrateEligibility` atomic flip + vector re-set), `:473-482` (`setRouter` unlink guard).
- Deploy callers register only real vault contracts: `contracts/script/DeployVaultRegistry.s.sol:145`, `contracts/script/BasketVaultDeployBase.sol:677`, `contracts/script/DeployPortfolioRouter.s.sol:139`. `RouterGovernance.sol` contains no registry lifecycle call; it only calls `router.setWeights` (`:196`).
- Test stand-ins prove EOAs are *intentionally* registrable: `contracts/test/VaultRegistry.t.sol:94-96` (`vault1/2/3 = makeAddr(...)`), `:132-203` (register + `setVaultStatus` on EOA `vault1` succeeds), `:542-554` (fuzz registers up to 30 fake EOAs successfully). Real-vault retire paths: `:275-341`, `:363-381`, `:766-821`; revert propagation on a hook that fails: `:389-405`.
- **Tests executed (this review, not inferred):** `FORGE_TEST_MIN_EXECUTED=1 bash .github/scripts/forge_test_require_executed.sh --match-path "contracts/test/VaultRegistry.t.sol"` → `44 passed; 0 failed; 0 skipped`, `executed-test-guard: 44 forge test(s) passed (floor 1)`.
- Solidity language semantics (external documentation, not a local execution): high-level external calls to a code-less address revert in 0.8.24 — either the compiler's `extcodesize` check (void function such as `retire()`/`unretire()`) or ABI decoding of empty return data. Labelled **reviewer inference from the pinned compiler's documented behaviour**; no local PoC tx was written (write scope limited to this file).

ANALYSIS:

- **Exact call sequence — EOA `E` (no code).** (1) ADMIN/timelock `registerVault(E, meta)` succeeds: nonzero and unregistered only; `_status[E]=Active`, `_registered[E]=true`, `E` appended to `_vaults`. (2a) `retire(E)` passes registered and not-eligible checks, writes `Retired`, then `IRetirableVault(E).retire()` reverts on the missing code → whole transaction reverts, status stays `Active`; `E` can never be retired via `retire()`. (2b) `reactivate(E)` likewise reverts. (2c) `setVaultStatus(E, Retired)` writes `Retired`, skips the hook because `E.code.length == 0`, and **succeeds**. So the documented asymmetry is real: `retire`/`reactivate` revert on an EOA while `setVaultStatus` silently succeeds. This is the entire substance of the first-pass observation.
- **Exact call sequence — non-vault contract `C` with code and no `retire()`/`unretire()`.** `registerVault(C, ...)` succeeds. `retire(C)` → hook call reaches a contract with no matching selector and no fallback → revert; status unchanged. `setVaultStatus(C, Retired)` → `code.length > 0`, same hook call → same revert; status unchanged. **Both paths fail closed.** A contract with a permissive fallback swallows the call on both paths; a contract whose hook reverts (e.g. registry-gated `retire` with wrong registry) reverts on both paths. In no contract case do the three functions diverge in final state — only the EOA case diverges.
- **Can the registry reach a WRONG state rather than an awkward one?** Checked each named example:
  - *"Retired status while deposits still work"* — **refuted**. For a real vault, every non-`Active` transition through `setVaultStatus` drives `retire()` and every `retire()` drives the hook (`VaultRegistry.sol:290,355-361`; `test_retire_setsRetiredStatusAndHaltsVaultDeposits`, `test_setVaultStatus_revertsWhenRetireHookReverts`). Even if a stale vector still names a vault that later becomes `Retired`, the router re-checks `status == Active` at deposit time (`PortfolioRouter.sol:1248-1252`) and reverts `VaultNotActive`. For an EOA/foreign contract there are no protocol deposits to "keep working".
  - *"A default vector pointing at a non-vault"* — **refuted**. `_requireRouterEligible` rejects `code.length == 0` with `VaultAssetUnreadable` (`PortfolioRouter.sol:1432`) and also requires `asset() == usdc`; an EOA registered in the registry therefore cannot be written into either the default or the active vector (`:1420`, `:596`). An EOA never receives USDC through the router.
  - *"A hook failure that blocks all registrations"* — **refuted**. `registerVault` never calls a hook; its only gates are role, zero address and duplicate. `testFuzz_listVaultsLength_equalsVaultCount` registers 30 fake EOAs in one test (executed above). A failing hook blocks only that vault's own `retire`/`reactivate`/`setVaultStatus` call.
  - *"A stuck eligibility/weight vector"* — **refuted**. `RetireWhileRouterEligible` (`VaultRegistry.sol:288,340-342`) precedes any status write; `setRouterEligible`/`migrateEligibility`/`setRouter` preserve the count/length invariant (`:381-482`). The code-check gap does not touch these guards.
  - The most that persists is *metadata*: `getVault(E)` can report `Retired` for an address that was never a vault. No user funds, routing leg, halt flag or count is wrong.
- **Prerequisite / trust boundary.** Registering a non-contract address is itself the root misconfiguration, and `registerVault` is `ADMIN_ROLE`-only, held solely by the `TimelockController` in production. Every downstream step is likewise `ADMIN_ROLE`-only. Nothing lower-privileged reaches the state: no public/unchecked caller, no cross-contract relay (grep of `contracts/**/*.sol` found registry lifecycle calls only in `VaultRegistry` itself, deploy scripts and tests), and the open timelock executor cannot alter the bound `(target, value, data, salt)` of a Safe-scheduled operation.
- **Front-run check.** A registration cannot be front-run by an untrusted party: only the timelock can call `registerVault`. A queued timelock action executes against the current proxy implementation; an upgrade that added a code check would make a queued bad registration revert, not bypass it. EIP-6780 prevents an existing vault from later losing its code, so a valid registration cannot silently decay into an EOA case.
- **Adversarial refutation summary.** The candidate fails the "reachable by anyone or an author" bar (requires a fully compromised/misconfigured timelock), fails the "wrong or falsely verified state" bar (all money-flow guards re-check code/status at write and deposit time), and fails safe on every reachable path (revert, never a silent mis-route with value). It is a genuine but cosmetic code-shape inconsistency plus a comment that overstates it, i.e. clarity only.

SEVERITY IF PROMOTED: **n/a**. If forced: `info` (clarity — inconsistent hook invocation and a comment that contradicts the EOA branch, with no material harm axis); `low` at the outside (release/assertion-adjacent harm that requires admin access and fails safe). Both are advisory and non-blocking. Confidence in the code-level asymmetry: `high`; confidence that no untrusted path exists: `high`.

RECOMMENDATION: No code fix required. Either (a) add the same `if (vault.code.length > 0)` guard to `retire` and `reactivate` for API consistency, or (b) keep the unconditional calls as the intended "fail loudly" behaviour, add a `code.length` check to `registerVault`, and correct the `setVaultStatus` NatSpec at `contracts/VaultRegistry.sol:322-328,348-354` so it no longer claims a missing hook always fails the call. Track as documentation/consistency hygiene (owner: code or decision); do not open a security issue at this pin.
