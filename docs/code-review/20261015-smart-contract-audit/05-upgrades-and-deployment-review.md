# Upgrades and deployment — source review

Review base: `3c753ff5b72f828f082673d4c5983418a418c47e` (15 October 2026). This review inspected the current UUPS library, proxy and timelock deployment path, storage gate, verifier, and upgrade-related release tooling. It is a source assessment. No Base RPC or deployed bytecode was checked.

## Findings

### UD-01 — Medium (release gate): a rewritten layout snapshot can make CI approve an incompatible upgrade

The active CI job runs `check-core-storage-layout.sh --selftest` and then its default same-tree comparison ([`.github/workflows/suite-01-02-forge-tests.yml:180`](../../../.github/workflows/suite-01-02-forge-tests.yml)). That script compares the freshly inspected layout against the snapshot **in the same checkout** ([`scripts/ci/check-core-storage-layout.sh:159`](../../../scripts/ci/check-core-storage-layout.sh), [`:177`](../../../scripts/ci/check-core-storage-layout.sh)). It offers `--write`, which replaces every snapshot with the current layout ([`:191`](../../../scripts/ci/check-core-storage-layout.sh)). The only arguments are default, `--write`, and `--selftest`; there is no deployed/release baseline comparison ([`:177`](../../../scripts/ci/check-core-storage-layout.sh)). The verifier derives a `layout_id` from that committed snapshot and the OpenZeppelin pins, without independently comparing it to compiled storage ([`publish-contracts/src/verify/upgradeability.ts:67`](../../../publish-contracts/src/verify/upgradeability.ts), [`:220`](../../../publish-contracts/src/verify/upgradeability.ts)).

Concrete sequence: an upgrade changes the order or type of two stored fields, then runs `check-core-storage-layout.sh --write` and commits the new JSON. Same-tree CI sees the new source and new snapshot match and passes. If the timelock installs that implementation, old proxy storage is read under the new layout. Depending on the changed fields, this can redirect assets or authority, or corrupt accounting. The source-level gate proves that the snapshot describes the **proposed** code; it does not prove compatibility with the implementation already holding user state. Compare the proposed layout against an immutable deployment/release anchor, and require a live proxy implementation/layout readback in the upgrade procedure. The October 15 security review recorded a fix for a similar gap; that fix's `storage_layout_gate.py --release-anchor` is absent from this checkout. Its disposition cannot be carried over to this commit.

This is a control gap for a **future governed proxy upgrade**, not an unprivileged path into the existing Base contracts. The [upgradeability plan](../../technical/contract-upgradeability-plan.md) says no upgradeable Robot Money deployment exists on Base 8453 and the existing mainnet contracts are direct deployments. Confirm actual deployment state before treating this as a live exposure.

### UD-02 — Medium (release readiness): this branch has no guarded operational upgrade/freeze path

`GovernedUpgrade.upgradeToAndCall` verifies only that the caller is the stored timelock, the proxy is not frozen, and the proposed code reports the ERC-1967 UUID; it does not check a reviewed build hash, layout, or linked-library identity ([`contracts/lib/GovernedUUPS.sol:97`](../../../contracts/lib/GovernedUUPS.sol), [`:140`](../../../contracts/lib/GovernedUUPS.sol)). This is a reasonable on-chain authority design **if** the operational path enforces those checks before the Safe schedules an upgrade. In the current tree, `publish-contracts/src/govern.ts` documents and implements other governance rows but contains no `upgrade-proxy` or `freeze-proxy` row; the storage gate has no prior-deployment anchor as noted above. The verifier can compare an implementation's linked libraries with a build artifact ([`publish-contracts/src/verify/upgradeability.ts:176`](../../../publish-contracts/src/verify/upgradeability.ts)), but that is a later observation, not a prerequisite to a timelock call. Thus the code reviewed here does not show a mandatory workflow that proves the implementation artifact, layout, and linked libraries before the Safe authorizes the write.

Concrete sequence: the timelock schedules and executes `upgradeToAndCall` for a UUPS-compatible implementation compiled from another source tree or linked against another `GovernedUpgrade` library. The proxy accepts it, because UUID compatibility alone does not prove intended behavior. This requires governance authority; it is not an unprivileged exploit. It makes the Safe review process and its release evidence the security boundary. Add an upgrade plan/readback gate tied to a fixed build SHA, storage anchor, linked-library runtime hashes, and target implementation hash before scheduling and after execution. The October 15 review describes an `upgrade-proxy` path and build provenance checks, but those tools are not present in this HEAD; historical status is therefore unverified for this branch.

The [release runbook](../../operations/contract-release-runbooks.md) explicitly tracks upgrade and freeze govern rows as future work. The existing Twin lifecycle rehearsal exercises the authority path; it does not make a production operator row or pre-schedule review gate mandatory. UD-01 and UD-02 share the missing release baseline but cover different checks: storage compatibility and authorization of the exact implementation artifact.

## Rechecked controls and historical items

- `GovernedUpgrade` keeps `upgradeTimelock` and `upgradesFrozen` in an ERC-7201 namespace; `init` is write-once, rejects a zero timelock and undeclared mode, and frozen-at-deploy sets the flag during initialization ([`contracts/lib/GovernedUUPS.sol:27`](../../../contracts/lib/GovernedUUPS.sol), [`:78`](../../../contracts/lib/GovernedUUPS.sol)). The base constructor disables implementation initializers ([`:180`](../../../contracts/lib/GovernedUUPS.sol)); upgrade/freeze entrypoints require an active proxy pointing at that implementation ([`:226`](../../../contracts/lib/GovernedUUPS.sol)).
- `freezeUpgrades` binds the live implementation address and code hash, then sets the one-way flag and disables future initializers in the proxy's OpenZeppelin namespace ([`contracts/lib/GovernedUUPS.sol:119`](../../../contracts/lib/GovernedUUPS.sol)). A queued upgrade subsequently fails at `_authorize` ([`:140`](../../../contracts/lib/GovernedUUPS.sol)). This is supported by current source, not a live-chain proof.
- Proxies are created with initializer calldata in the ERC-1967 constructor, avoiding a public initialization interval in the script path ([`contracts/script/UpgradeAuthority.sol:110`](../../../contracts/script/UpgradeAuthority.sol)). The timelock stage checks each handed-over proxy reports the deployed timelock ([`contracts/script/DeployTimelock.s.sol:946`](../../../contracts/script/DeployTimelock.s.sol)). The manifest records implementation hashes for router and vaults ([`:1102`](../../../contracts/script/DeployTimelock.s.sol), [`:1134`](../../../contracts/script/DeployTimelock.s.sol)).
- The current layout gate inventories ten proxies, storage rows, structs, enum members, linked-library names, ERC-7201 namespace declarations, and OpenZeppelin gitlinks ([`scripts/ci/check-core-storage-layout.sh:42`](../../../scripts/ci/check-core-storage-layout.sh), [`:56`](../../../scripts/ci/check-core-storage-layout.sh), [`:133`](../../../scripts/ci/check-core-storage-layout.sh)). These checks are useful for same-tree consistency but do not close UD-01.
- The upgrade entrypoint forwards through an externally linked `GovernedUpgrade` library by `delegatecall` ([`contracts/lib/GovernedUUPS.sol:223`](../../../contracts/lib/GovernedUUPS.sol)). The verifier recursively reads linked addresses from runtime bytecode and compares on-chain library code to build artifacts ([`publish-contracts/src/verify/upgradeability.ts:176`](../../../publish-contracts/src/verify/upgradeability.ts)). This has to be run against the exact production build and live proxy; an implementation hash alone identifies the embedded library address, not the code executing there.

## Limits and release checks

The review did not reconstruct CREATE2 addresses, run a full build from the commit, compare compiler settings and the Solidity known-bugs list, or inspect any live proxy implementation slot, library code, frozen state, initialized version, timelock delay, Safe owners, or deployed bytecode. Those checks, plus a storage comparison from **the live implementation** to the proposed one and a verified post-upgrade readback, are required before a release verdict. Review each new reinitializer and migration against existing roles, positions, and exclusion claims. Linked library and OpenZeppelin source changes need their own behavioral assessment even when the storage shape is unchanged.
