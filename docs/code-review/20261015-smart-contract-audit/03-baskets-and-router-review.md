# Chapter 03 audit notes: baskets and router

Target: `3c753ff5` (`review/contracts-security-20261015`). This is a source review of the basket, price recorder, swap adapters, router, router governance, deploy guards, and relevant prior reviews. It is not a deployment attestation or a completed economic simulation.

## Candidate finding C-03-01: a V3 oracle pool can differ from the execution pool

**Disposition after design review:** Retained. [ORA-3](../../technical/smart-contract-invariants.md) requires the pricing pool to be the pool trades execute against. The registry marks it as holding, but its V3 evidence compares only the fee tier after the supplied pool is accepted. The finding stays conditional on an authorized misconfiguration.

**Status:** Source-confirmed validation gap; economic impact is conditional and has not been reproduced on a fork. **Prerequisite:** an authorized `ADMIN_ROLE` call to `BasketVault.addAsset`, or a deployment configuration accepted by the scripted asset stage, supplies a V3 `pool` address from another factory (or a contract that implements the expected pool reads) for the correct token pair and fee. An unprivileged caller cannot change the registered pool.

`BasketAssetConfigGuard.requirePoolUsable` verifies `token0`, `token1`, observation history, and liquidity (`contracts/lib/BasketAssetConfigGuard.sol:110-127`). `requireExecutionPoolMatchesTwap` then compares only `pool.fee()` with `swapFee` for V3 (`contracts/lib/BasketAssetConfigGuard.sol:250-264`). The deploy script repeats the fee and liquidity checks, but does not look up the canonical pool from the swap router's factory (`contracts/script/BasketVaultDeployBase.sol:521-533`). The default V3 swap path passes token addresses and fee to `SWAP_ROUTER.exactInputSingle`, with no pool address (`contracts/lib/BasketSwaps.sol:76-96`); the optional V3 adapter does likewise (`contracts/adapters/UniswapV3SwapAdapter.sol:86-99`). Thus the venue that prices NAV and minimum outputs can differ from the venue that settles trades. The V4 adapter checks its recorder and complete pool ID at construction and on TWAP reads; the Aerodrome adapter resolves its canonical factory pool, so this candidate concerns the V3 paths.

**Concrete sequence to test:** An operator registers a token/USDC pool from a different V3 factory with the same fee and enough observations. Its observed price is much higher than the canonical execution pool's. `BasketVault.totalAssets` marks existing token balances at that higher price (`contracts/vaults/BasketVault.sol:524-535`), and the deposit deviation check compares this pool's own spot with its own TWAP (`contracts/lib/BasketViews.sol:109-127`), so that check does not detect the cross-pool disagreement. A subsequent deposit executes on the canonical pool at the lower token price (`contracts/vaults/BasketVault.sol:670-719`); its minimum token output is based on the higher oracle price, so the buy can pass. Share minting uses the mismatched post-swap NAV delta over pre-deposit NAV (`contracts/vaults/BasketVault.sol:618-663`). When the existing basket's token mix differs from the new equal-weight buy, the mismatch can under-mint the new depositor and transfer value to existing holders. For illustration only, if the vault holds 100 units of A worth $1 each, the registered A oracle marks them at $10 each, and a new $20 deposit buys 10 A plus $10 of newly listed B at honest prices, the new deposit is marked at $110 against $1,000 pre-deposit NAV. Ignoring fees and virtual-share rounding, it receives about 9.9% of the resulting shares, worth about $11.9 of the $120 true backing. This is an example, not measured production loss. A falsely high mark can also raise sell minimums above executable output and block USDC redemptions; `redeemInKind` remains available.

**Needed to confirm and size:** Construct a same-pair, same-fee alternate-pool fixture, register it through `addAsset`, then exercise multi-asset deposit, redemption, and the deployment script. Query the exact router/factory used in a target deployment and compare `factory.getPool(token, USDC, fee)` to every registered V3 pool. The loss depends on the relative pool prices, asset mix, caps, slippage settings, and the availability of an alternate pool accepted by governance. Enforce canonical pool identity at registration and in the deploy stage, using the same factory the swap router executes against.

The numerical example above also depends on a TVL cap that permits the inflated pre-swap NAV plus deposit and on subsequent operations accepting the resulting NAV. `_deposit` checks `taBefore + usdcAmount` before swaps but does not recheck post-swap NAV against `tvlCap` ([`BasketVault.sol:620-630`](../../../contracts/vaults/BasketVault.sol)); determine whether the mismatched mark can make post-swap NAV exceed the cap and quantify it in the same fixture. This is a conditional consequence of C-03-01, not an independent finding at this stage.

## Reclassified C-03-02: degraded-oracle recovery sends returned assets to a fixed address

**Disposition after design review:** Documented behavior, removed from the vulnerability count. One operational verification item remains. The [security model](../../technical/security-model.md) §3 specifies this path: when a removed asset's TWAP read reverts, `BasketSwaps.reabsorb` sends the balance to the fixed `ForeignTokenQuarantine.QUARANTINE`. An earlier draft of this chapter said the path contradicted the design. That claim was wrong. Recovery from quarantine is an offline governance process. The open question is whether governance actually controls the quarantine destination on the target chain and can return the funds to holders.

`reabsorbRemovedAsset` is permissionless. If its TWAP read reverts, the catch branch sweeps the entire inactive-token balance to `ForeignTokenQuarantine.QUARANTINE` ([`contracts/lib/BasketSwaps.sol:157-174`](../../../contracts/lib/BasketSwaps.sol)); this path bypasses `minUsdcOut` because that floor is checked only inside the successful `try` branch. The destination is the fixed `0x0000000000000000000000000000000000deaD11` constant ([`contracts/lib/ForeignTokenQuarantine.sol:44-49`](../../../contracts/lib/ForeignTokenQuarantine.sol)), while BasketVault has no quarantine-address setter or recovery entrypoint. Existing `test_LIFE6_reabsorbSurvivesDegradedPool` asserts that a stranger can trigger a 7-USDC-value token balance transfer there ([`contracts/test/BasketVault.t.sol:588-615`](../../../contracts/test/BasketVault.t.sol)); its comments call this destination governed and reversible, which the current BasketVault source does not establish.

The PRD expects quarantined tokens to be recoverable through governance (`docs/prd.md:675-685`, `contracts/vaults/BasketVault.sol:1170-1207`). Verify the fixed address's code, control, and recovery runbook on the intended chain. Do not call the balance lost without that evidence.

## Remaining work and limits

- Run the C-03-01 fixture and verify registered pool identity against the actual execution factory for each deployed V3 leg.
- Measure V4 held-price and sampling scenarios on the exact deployment configuration. The October 14 901-slot, 240-second result does not itself prove the new 7,201-slot sell-anchor deployment. Confirm live ring, recorder age, keeper cadence, pool depth, caps, and the vault implementation before applying either conclusion.
- Exercise emergency override, degraded-pool quarantine, dust accumulation, and post-removal reappearance with exact token behavior. Source inspection alone cannot establish recoverability of a quarantined balance or executable exit prices under stressed liquidity.
- Trace the emergency override configuration and authority: `setEmergencyUnwindGuard` accepts `maxLossBps == 10_000`, making `appliedFloor` zero for any configured reference floor, while override execution is EMERGENCY_ROLE-gated ([`BasketVault.sol:1318`](../../../contracts/vaults/BasketVault.sol), [`:1470`](../../../contracts/vaults/BasketVault.sol), [`BasketSwaps.sol:121`](../../../contracts/lib/BasketSwaps.sol)). Disposition against June SR-M17 and verify the live role topology. The zero-floor override is documented governance authority, so record it under assumptions and operational limits, not in the vulnerability count.
- Record transaction-expiry behavior. Basket deposit/redeem and router deposit routes do not expose a caller deadline; swaps pin their adapter deadline to `block.timestamp`, while `PortfolioRouter.redeemFor` accepts a caller deadline ([`BasketVault.sol:552,732`](../../../contracts/vaults/BasketVault.sol), [`BasketSwaps.sol:67-96`](../../../contracts/lib/BasketSwaps.sol), [`PortfolioRouter.sol:988-997`](../../../contracts/PortfolioRouter.sol)). Assess pending-transaction risk and signed floor protection; do not treat the current-block adapter deadline as user transaction expiry.
- Complete source checks for token ordering/decimals, return-array lengths, checked casts, router cap and zero-weight cases, migration interlocks, role holders, and preview-to-execution state changes. These outline items remain open rather than implicitly covered.
- Recheck gas and external-call behavior for the target chain and contract set. No tests, fork simulation, or live-state reads were run for this chapter.
