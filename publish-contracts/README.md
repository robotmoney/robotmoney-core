# publish contracts

This CLI is the ONLY deploy driver (core's old runner `scripts/deploy/core-stages.ts` and the post-stage assert scripts are deleted; their checks are labels of the one verifier). One Bun TypeScript CLI runs every contract deploy (devops issues 61, 55 and 58). It runs on the Twin chain (918453) and on Base mainnet (8453). A rehearsal and production differ only in the arguments. The Twin chain is a pinned lazy fork of real Base state (see the Twin chain section below). There is no mock Safe, no scripted Safe and no shell orchestrator. The operator runbook is `docs/runbooks/publish-contracts.md`. This file documents the tool and lists the remaining gaps.

## Run it

Operator helpers that replaced shell scripts: `bun run ops derive-agents`, `bun run ops fee-estimate` and `bun run ops sourcify-submit` (`src/ops`).

```
cd publish-contracts && bun install
bun src/cli.ts --chain 918453 --rpc $RPC --sheet evidence/<run>/frozen-sheet.env \
  --signer keystore:/dev/shm/rh/keys/DEPLOYER --environment local --core-sha <40-hex DEPLOYER SHA> \
  [--stage plan|deploy|all|a,b] [--resume] [--dry-run]
```

| Argument | Meaning |
|---|---|
| `--chain` (alias `--chain-id`) | Target chain id. Must equal `cast chain-id` of the RPC. Only 8453 and 918453 run. |
| `--rpc` | RPC URL. It reaches forge and cast through `ETH_RPC_URL`, never as an argument. |
| `--sheet` | The frozen sheet. Parsed as data. Never sourced. |
| `--signer` | `keystore:PATH`, `env:signer` (the caller's credential tool sets CHAIN_SIGNER_KEYSTORE and CHAIN_SIGNER_PASSWORD), `ledger` or `trezor`. Never a key. A keystore passphrase file is refused on 8453. |
| `--environment` | GitHub Environment name, or `local`. |
| `--core-sha` (alias `--deploy-sha`) | Core DEPLOY_SHA, 40 hex. The core checkout HEAD must equal it. |
| `--stage` | `plan` (checks only, no signer), `deploy` (through timelock), `all` (adds verify and govern), or a comma list. Default: through verify. |
| `--system` | `vaults` (default) or `gateway` (issue 1892). The two systems deploy, verify and record evidence independently. `gateway` runs the stages `gateway` and `gateway-handover` against the vaults system's manifests, with its own small sheet (`GATEWAY_ADMIN_ADDRESS` and `GATEWAY_UPGRADE_TIMELOCK`, no default, no `AGENT_*`, no Safe), its own `--evidence` directory and its own verifier; only `publish` and `verify` run in it. Runbook: `docs/operations/contract-release-runbooks.md` 4.13. |
| `--resume` | Continue a run: adopt the existing Safe, skip finished stages, continue a dead broadcast with `forge --resume`. |
| `--logs-rpc` | A run that reaches prove-control (QA plan v1 E7, issue 1724): the RPC the `--resume` adoption reads the Safe's execution events from (`eth_getLogs`, after one `eth_chainId` read that must answer `--chain`, else `LOGS_RPC_WRONG_CHAIN`, exit 5). Every other read stays on `--rpc`. Use it when the `--rpc` provider rate-limits or caps `eth_getLogs` (mainnet.base.org did on the first mainnet run): no local router is needed. Refused (`USAGE`) on a run with no prove-control step. Only its host is logged. |
| `--dry-run` | The preflight: every check, then a forge simulation of EVERY deployer stage in order (the four vault scripts included) on a local anvil the CLI starts itself on a loopback port: a lazy fork of `--rpc` with the target's chain id (8453 for a mainnet sheet). Each stage, the Safe included, is then applied to that anvil by the impersonated deployer, so earlier stages make the inputs of later ones. The impersonated sender is keyed on the loopback RPC, never on the chain id: an 8453 sheet's preflight passes the safe stage, and any non-loopback RPC is refused at every chain id (issue 1720). Nothing is broadcast, nothing is sent to `--rpc`, and the checkout is left as found. `--signer address:0xADMIN` is accepted here only (no secret). |
| `--measure` | Rehearsal only. Learn the per-stage counts and write `deployments/frozen-counts/<sha>.json`. Without the flag a missing counts file means: `--dry-run` warns (`dry_run.counts_missing`) and prints `dry_run.counts_measured`, writes nothing; a broadcast on the Twin chain measures and writes the file (`counts.measuring`); a broadcast on 8453 fails `COUNTS_MISSING`. `--stage plan` always needs the file. |
| `VERB` | Optional first word: `publish`, `verify`, `govern`, `pause-all`, `record-receipt` or `redeploy-vault`. See Core harness contract. |
| `--row` | Govern only: one row, by number or name. |
| `--vault` | `redeploy-vault` only: the vault to redeploy. `PROTO` is the only one (issue 1796). |
| `--prior-out` | `verify` only, after a `redeploy-vault` round at another SHA: the forge `out/` of a git checkout built at the ORIGINAL deployment SHA (its HEAD must be that SHA). Every contract the redeploy did not replace is compared with it; the replacing vault with this checkout's build (QA plan v1 E1). After such a round the verify runs ALONE at the redeploy SHA with `--prior-out`. Every other run that reaches the verify stage (the default stage set, `--resume` included, `--stage all`, a `--stage` list naming verify and another stage) is refused (`USAGE`) before any signer, at the original SHA and at the redeploy SHA, and a `--prior-out` that is not a checkout of the original SHA is refused on all of them. The verify stage refuses a wrong build once more itself (`verifyBuildRefusal`) and pauses nothing. `evidence-check` then requires `verified_at_sha` (the round's SHA) and `prior_out_sha` (the evidence `core_sha`) on every round. |
| `--owner-signer` | prove-control and govern: a Safe owner signer spec, repeated. prove-control needs one for EVERY Safe owner (on 8453 a run that reaches prove-control with fewer specs than the sheet has owners, the same spec twice, or two specs claiming one owner is refused before stage 1 with `CONTROL_NOT_PROVEN`, exit 24, so no stage broadcasts first). Govern needs the threshold. An owner is an encrypted keystore, `keystore:PATH`, or, at that owner's choice, a hardware wallet bound to its owner: hardware is optional, never required (owner decision 2026-10-14). A hardware owner is `ledger:PATH@0xOWNER` or `trezor:PATH@0xOWNER` (PATH like `m/44'/60'/0'/0/0`): the tool asks for that device, refuses unless it reports the named owner (`HARDWARE_ADDRESS_MISMATCH`), refuses two specs that resolve to one address, and asks for the device again and re-checks it before each signature. Example: `--owner-signer "ledger:m/44'/60'/0'/0/0@0xOWNER1" --owner-signer "ledger:m/44'/60'/1'/0/0@0xOWNER2" --owner-signer "trezor:m/44'/60'/0'/0/0@0xOWNER3"`. |
| `--logs-rpc`, `--logs-window`, `--logs-tries` | prove-control `--resume` only (issue 1724): a separate RPC for `eth_getLogs` alone, the blocks per call (default 2000), and the tries of one throttled call (default 6). See prove-control under Verify and govern. |
| `--emergency-signer` | pause-all, and the automatic pause after a failed verify: the EMERGENCY key signer spec. Needed once the stage 11 handover has begun. On the Twin chain with none given: the EMERGENCY keystore beside the DEPLOYER keystore. Never defaulted on mainnet. |
| `--core-dir`, `--evidence`, `--counts-dir`, `--compare-sheet`, `--max-wait` | Paths, the sheet to diff in the isomorphism report, and the longest govern wait. |
| `--no-warp` | govern only: no Twin time warp, so a wait over `--max-wait` exits 15 (`GOVERN_PENDING`) as on 8453 (issue 1859; the Twin upgrade rehearsal stops the freeze row after its schedule this way). |
| `--counts-require-origin-dev` | 8453, reconstructed baseline: also refuse unless HEAD of the counts checkout is reachable from its local `origin/dev` (fetch it first). Off by default in code, required by the release runbook. |

Caller environment only: `YES=1` (refused on 8453) and `CONFIRM=typed|environment` (`environment` only in GitHub Actions behind an Environment with reviewers). They are never sheet lines. On 8453 `CONFIRM=environment` is accepted on one proof only (qa-plan B2, DT-3): the job's GitHub OIDC token, which the CLI fetches through the runner's `ACTIONS_ID_TOKEN_REQUEST_TOKEN`/`_URL` (the job needs `id-token: write`) for the audience `robotmoney-publish-contracts`, verifies against GitHub's JWKS, and accepts only when its `environment` claim equals `--environment`, its repository is owned by `robotmoney` and its subject is the environment-gated job's (`repo:OWNER/REPO:environment:NAME`). `GITHUB_ACTIONS=true` on a laptop is refused by name (`FLOOR`, exit 4); a token that does not verify is a refusal, never a skip; the token is never logged. The check runs before any signer exists and again at every broadcast (`src/actions-proof.ts`).

## Core harness contract (positional verbs, `--row`, stdout rows, `PUBLISH_MANIFEST_DIR`)

Core's Twin harness is the consumer of this CLI (`testing/smoke-test/src/publish.rs`, `testing/fork-e2e-rust/src/deployed.rs` and `scripts/stage/core-stack.ts`, all in this repo). The CLI adapts to it. `tests/core-harness-contract.test.ts` spawns the CLI as a child process with exactly the argument vector and environment core builds, and asserts what core reads back.

What core sends:

```
bun src/cli.ts VERB --chain 918453 --rpc RPC --sheet SHEET --signer keystore:KEYDIR/DEPLOYER:PASSFILE \
  --environment stage --core-sha SHA [--row ROW]          (env: PUBLISH_MANIFEST_DIR=<work dir>/manifests, stdin: null)
```

| Verb | Same as | Notes |
|---|---|---|
| `publish` | `--stage deploy`: safe, then every table stage through timelock, with prove-control just before timelock | Refuses a stage whose manifest already exists, like `--stage deploy`. |
| `verify` | `--stage verify` | A follow-on verb: it implies `--resume`, so it reads the run manifest of `publish`. |
| `govern` | `--stage govern` | A follow-on verb: it implies `--resume`. |
| `redeploy-vault` | none: a verb of its own (issue 1796) | `--vault PROTO`. Redeploys ONE vault into the live deployment the `--evidence` run made (its timelock stage done). The DEPLOYER (`--signer`, the sheet's ADMIN_ADDRESS) runs `RedeployProtocolAssetVault.s.sol`: a new rmPROTO, paused before its first asset is added, unregistered, unlinked, `ADMIN_ROLE` on the timelock and `EMERGENCY_ROLE` on the emergency key. The new vault must be the deployer's CREATE in the broadcast receipts. It is a governed proxy, read back with the runner's proxy gate checks (issue 1809, QA plan v1 L1): the implementation slot names the manifest's `vault_implementation`, no admin or beacon, `upgradeAuthority()` is the timelock, the sheet's `UPGRADE_MODE`, initialized, implementation locked. A miss is `VERIFY` and the old vault manifest stays. The round keeps the read as its `proxy` record. The verb keeps the old vault manifest as `<manifest>.retired-N.json`, writes the new vault into the vault manifest and records the round in `publish-run.json` `vault_redeploys` (saved only after the typed confirmation; `--resume` continues a dead broadcast). Next: `govern --row redeploy-vault`. Rehearsal and Twin only: refused on 8453 in production before any signer. `--dry-run` simulates only. |

A verb and `--stage` are not combined (usage error, exit 2). `--stage` still works alone. `--row N` or `--row NAME` runs one govern row (govern only). The rows, in order: `unpause-USDC`, `unpause-PROTO`, `unpause-AGENT`, `unpause-RWA` (all four vaults deploy paused; the only mainnet operations after the timelock handover), then `update-delay`, `batch`, `cancel` (Twin-only demonstrations of the Safe tool, refused with USAGE on 8453, by name and by number). Without `--row`, every unpause the sheet asks for is scheduled in one sitting. The unpauses have no order among themselves. A Twin-only row starts only when every earlier row is complete. A phase already recorded in the run manifest is not sent again, and its line is printed again. An unknown row or number is a usage error. A single-row run does not mark the govern stage done (the run that finds every row of the chain complete does: the four unpauses on 8453, all seven on a Twin fork). `--row release-receipt --receipt-id 0x<bytes32>` is refused with USAGE once RouterGovernance holds the receipt contract's `ADMIN_ROLE` (every deploy since core 1698; issue 1831): a release alone would burn the receipt, so a receipt is released only by `--row apply-receipt`, which also refuses a receipt not recorded after RouterGovernance's `lastAppliedRecordedAt`. On a deployment where RouterGovernance does not hold that role it is an on-demand row, outside that order: it releases one recorded consensus receipt (`ConsensusRecommendationReceipt.releaseReceipt`, whose `ADMIN_ROLE` the timelock holds after the timelock stage) as its own Safe -> Timelock round, on 918453 and on 8453 (core 1611). On 8453 it is a standalone post-launch action, never part of stage 13, which stays the four unpauses: the first run schedules and exits `GOVERN_PENDING` (15) with the resume command, and the same command after the 48-hour delay executes it and reads `isReleased` back. The evidence check takes it under `receipt_releases`. It neither waits for nor completes the ordered rows. Its run-manifest key and salt are `release-receipt-<receiptId>`, so one receipt is one operation, a rerun reprints its lines with no new transaction, and a record under that key for a different operation is refused. It refuses, before the Safe schedules anything, a receipt that is not recorded or is already released by some other operation. Its lines carry `"row":"release-receipt"`. `--receipt-id` without that row is a usage error.

What core reads back:

- **Exit code.** 0 on success. A failure has its own code (the table under Exit codes). Core passes it through.
- **Govern stdout.** One JSON line per round event that sent a Safe transaction: `{"row":"unpause-PROTO","phase":"scheduled","txHash":"0x...","status":1,"readyAt":1700172800}`. `phase` is `scheduled`, `executed` or `cancelled` (the Twin-only cancel row ends in `cancelled`, every other row in `executed`). `status` is the receipt status of the Safe transaction (1 success, 0 reverted). A revert also stops the run with exit 14, so a printed line has status 1. `readyAt` is the unix time the timelock operation becomes executable (schedule time plus the real delay). A basket the sheet does not unpause (`GOVERN_UNPAUSE_VAULTS`) stays paused: its row is skipped and prints no line. Nothing else is printed on stdout by govern. The structured log (`govern.safe_tx` and every other event) stays on stderr, one JSON object per line. Core's `parse_govern_output` keeps the lines that start with `{` and carry a `row`. The recorded sample both repos test against is `tests/fixtures/govern-stdout.jsonl` (the same file sits in core at `testing/smoke-test/tests/fixtures/`). To re-record it: `RECORD_GOVERN_FIXTURE=1 bun test tests/core-harness-contract.test.ts`, then copy it to core.
- **Verify stdout.** The verifier labels: a `[verify]` line, then one label per line (the format of `tests/fixtures/verifier-labels.txt`). Pass or fail is the exit code, and each check is a `verify.check` log line on stderr. Core diffs the labels against mainnet's. The four `agents:` labels are negative-invariant checks: each passes only when something is absent (no `AgentAuthorized` or `AgentOwnershipTransferred` log since the deploy began, zero listed agents, no `AGENT_ROLE` holder, no deployer-owned agent), because the deploy authorizes no agent (core 1527; architecture 5.2 and 6.3). They are not dead code.
- **Manifest directory.** `PUBLISH_MANIFEST_DIR` names where the stage manifests go (`safe.json` and every file core's stage table names). forge gets it as an absolute `DEPLOYMENT_OUT`, and govern, verify and later stages read from it. Unset, the CLI uses `deployments/<chain>/` in the core checkout. The directory must be one forge may write: core's `foundry.toml` `fs_permissions` allow `./deployments` and `/tmp`.

Defaults that keep core's vector working without extra flags:

- No `--core-dir`: the repo root (the nearest parent of the working directory, else of this package, with `scripts/deploy/stage-table.json`). `--core-dir` is only for a checkout elsewhere.
- No `--counts-dir`: `deployments/frozen-counts` in the working directory if it exists, else this repo's.
- No `--owner-signer` on chain 918453: the rehearsal's own `SAFE_OWNER_A`, `SAFE_OWNER_B` and `SAFE_OWNER_C` keystores beside the `DEPLOYER` keystore, under the same passphrase file (the layout `src/rehearsal/keys.ts` writes). Never on 8453, where every owner is named by `--owner-signer`: `keystore:PATH`, opened with a passphrase typed at a hidden prompt, or a device bound to its owner, `ledger:PATH@0xOWNER` / `trezor:PATH@0xOWNER` (hardware optional, never required; a bare `ledger` is a usage error, it names no owner).
- An unattended run (stdin null) needs `YES=1` in the inherited environment. Without it the CLI refuses with exit 17 and sends nothing. `YES=1` is refused on 8453.

The test doubles in that test (stub forge and cast, a fake Safe API and timelock) stand in for tools and the chain. They check the CLI surface. They are no evidence for the Safe, its signers or governance: that is proven on the real deployment (devops `CLAUDE.md`, item b).

## Stages (data from core's stage table)

**Deployed release (v0.5.0).** The deployed v0.5.0 release ran an `ic-policy` stage and registered the submitter with `register-committee`. Since issue 1888 (owner decisions 2026-10-19 and 2026-10-20) the `ic-policy` stage is gone, a `receipt` stage deploys `ConsensusRecommendationReceipt` on its own, the submitter is registered by the `register-submitter` row (one `grantRole(RECEIPT_SUBMITTER_ROLE, safe)` timelock call) and there is no `transferAgentOwnership`. Historical `register-committee` evidence still validates (see below).

The stage table is DATA: `scripts/deploy/stage-table.json` (version 1) at the repo root (see `scripts/deploy/README.md`). `src/stage-table.ts` reads it from the repo root at the start of every run (`--core-dir` only names a checkout elsewhere, such as the one devops makes). This package keeps no forge script path, required env name, artifact name, library name or manifest name of its own. There is no second runner: core's old runner is deleted.

Order: safe (the real Safe, from `src/safe`), then the table's stages in table order (libs, recorder, vault, registry, router, gateway, receipt, governance, proto, agent, rwa), then `prove-control`, then timelock, verify and govern. `src/stages.ts` builds the rows from the table and adds only those four orchestration rows. A vault is a row, so one loop registers, hands over and verifies all four.

What the table does not carry lives in ONE mapping module, `src/core-wiring.ts`: which sheet name feeds which env name (core's env name `TVL_CAP` is fed by the sheet name `VAULT_<KEY>_TVL_CAP`, with the vault key in it, and there is no unprefixed `VAULT_TVL_CAP`; `FEE_RECIPIENT` is `FEE_RECIPIENT_ADDRESS`, `SEED_SHARE_RECEIVER` is `SHARE_RECEIVER_ADDRESS`, `SWAP_ROUTER` is its own sheet name), which earlier manifest field feeds which env name (`REGISTRY_ADDRESS` is the registry stage manifest's `registry`, `VAULT_ADDRESSES` is the `vault` field of every table vault), and which manifest fields the verifier reads. Basket stages (rmPROTO, rmAGENT, rmRWA) get `--libraries <path>:<artifact>:<address>` for every library the table lists, the address read from the libs stage manifest under the table's `manifestKey`. The verifier checks each vault against the table's `vaults[].artifact` (rmRWA is `RwaBasketVault`, rmAGENT is `AgentTokenVault`), each library against `libraries[].artifact` and each core contract against `artifacts`.

Core parity (`src/ci/core-parity.ts`, `tests/core-parity.test.ts`): reads the repo root and fails, naming the row, when a stage's script or contract is missing, a required env name is not read by that script, a manifest file is not written by it, a manifest field the tool reads is not serialized, or an artifact does not exist. It runs with every other test in `bun test` (the repo root is found by walking up, there is no `CORE_DIR` variable). The CI job `publish-contracts-tests` (`.github/workflows/suite-28-core-stages.yml`) runs `bun install --frozen-lockfile`, `bun x tsc --noEmit` and `bun test --timeout 60000` in this directory and fails when the pass count is zero. All tests load the same table through `tests/preload.ts` (`bunfig.toml`).

**Governed proxies (issue 1809, ADR-0014).** The table's `proxies` lists the nine contracts that run behind their own `ERC1967Proxy` (rmUSDC, registry, router, gateway, receipt, governance, rmPROTO, rmAGENT, rmRWA; v0.5.0 also had the IC policy proxy, retired by issue 1888). Each has a layout snapshot under `contracts/test/fixtures/storage-layout/` (one JSON per contract plus `pins.json`), checked by core parity and `scripts/deploy/stage-table.test.ts`. Each proxy stage deploys the implementation, then the proxy whose constructor runs `initialize` in the same transaction (`_deployProxy` in `contracts/script/UpgradeAuthority.sol`), and its manifest names the proxy, the implementation (`<field>_implementation`), `upgrade_authority` and `upgrade_mode`. There is no authority stage. Every proxy names, from its first block, the one `ProposerFloorTimelock` the `timelock` stage deploys LAST at the CREATE2 address predicted from `SAFE_ADDRESS` and `TIMELOCK_MIN_DELAY` (`UpgradeAuthority.predictTimelock`; the pin and adoption rules are under Governed proxies below), so the role handover and the upgrade authority are one timelock. `UPGRADE_MODE` comes from the sheet (below). The parser refuses a table whose proxy stage does not require `UPGRADE_MODE`. Right after each proxy stage the runner reads every proxy it deployed back from the chain (`proxyStageGate` in `src/runner.ts`, `src/proxies.ts`): the ERC-1967 implementation slot names the manifest's implementation, the ERC-1967 admin and beacon slots are empty, `upgradeAuthority()` is the authority stage's timelock, the manifest's `upgrade_mode` is the sheet's and `upgradesFrozen()` agrees with it, the proxy is initialized and the implementation's initializers are locked. A read that differs is read again, up to 5 times 1 s apart, like every read after a landed transaction (QA plan v1 E6). Any miss that remains (an undeclared mode, an unexpected admin slot, another implementation) is `VERIFY` (exit 13): the stage's record keeps `proxy_gate: { ok: false, problems }` and no later forge stage starts while it does. Each stage record keeps the proxies it read (`proxies`: proxy, implementation, both code hashes, authority, mode, frozen, whether the admin and beacon slots are empty). A dry run reads the proxies back on its local chain.

Per stage: inputs, start nonce (must equal the summed frozen counts of earlier stages, plus the one prove-control transaction for every stage after it), simulate, dry-run count equals frozen count, confirmation, broadcast, broadcast count and nonce delta equal the frozen count (hard failure otherwise), manifest written. The run manifest `evidence/.../publish-run.json` keeps each stage's start nonce and count.

Reads after a landed transaction (issue 1723, QA plan v1 E6). A load-balanced RPC such as mainnet.base.org may answer a read from a node that has not seen the newest block yet. So every read that checks what a landed transaction left is read again until the expected state shows: up to 5 reads, 1 s apart (`src/safe/read-after-write.ts`). The sites are the Safe creation (connect, `verifyCreatedSafe` and the deployer nonce, in `awaitCreatedSafe`), the Safe nonce after an execution (`awaitSafeNonce`), the prove-control entry (a Safe nonce of 0 leads to a new proof only when every read says 0), the stage 11 gate (with a finished proof on record it waits for nonce 1 or more), and the `redeploy-vault` verb (the deployer nonce after the broadcast and the state of the new vault). A state that still differs after the last read fails with the same error as one read would, and the message names the reads and the RPC host. A value past the expected one (a nonce above it) fails at once.

## Sheet, floors and counts

- `src/sheet.ts`: whitelist parser. `SWAP_ROUTER` is the Uniswap V3 SwapRouter02 the basket scripts read. Per-vault names `VAULT_<USDC|PROTO|AGENT|RWA>_TVL_CAP`, `_PER_DEPOSIT_CAP`, `_EXIT_FEE_BPS`, and for the baskets only (`PROTO|AGENT|RWA`, a `USDC` name is refused) `_NAV_DEVIATION_BPS` (1 to 2000, never 0) and `_MIN_POOL_LIQUIDITY` (above 0, `pool.liquidity()` units, not USDC). Everything is required. Values that stages produce (`REGISTRY_ADDRESS` and so on) are refused. The example is `tests/fixtures/frozen-sheet.env.example`, and a test runs it through the real parser.
- `UPGRADE_MODE` (issue 1809, ADR-0014 §5): `upgradeable` or `frozen`, required, no default. Every proxy stage passes it to `initialize`, the runner and the verifier compare every proxy with it, and any other value (`unset` included) is refused by the sheet parser before any stage runs. `upgradeable` is the mode of the Twin, a rehearsal, a contained mainnet test and a final release with a proving period; `frozen` fixes a final release at launch.
- `src/sheet.ts` floors on every chain: a zero TVL cap is refused, the per-deposit cap is never above the TVL cap, `exitFeeBps` is at most the vault maximum read from core's `MAX_EXIT_FEE_BPS` (100 today) at the DEPLOY_SHA, `FEE_RECIPIENT_ADDRESS` is never zero or `ADMIN_ADDRESS` (the deployer) and may be `@safe`. `USDC_ADDRESS` is a constant (`src/usdc.ts`), not a sheet value: the example sheet has no line for it and a sheet that carries one must name the constant.
- `src/floors.ts`: keyed to the chain id read from the RPC. Delay floor 172800 on 8453, at least 1 elsewhere. `EXPECTED_CHAIN_ID` and `CHAIN_ID` must equal the RPC chain id. `YES` and plaintext signing are refused on 8453. No flag lifts a floor. `CONFIRM=environment` on 8453 is accepted only with the Actions-only proof below.
- `src/actions-proof.ts`: the Actions-only proof behind `CONFIRM=environment` on 8453 (qa-plan B2, DT-3). The runner of a job with `id-token: write` sets `ACTIONS_ID_TOKEN_REQUEST_TOKEN` and `ACTIONS_ID_TOKEN_REQUEST_URL`; the CLI asks it for a token with audience `robotmoney-publish-contracts`, verifies the RS256 signature against `https://token.actions.githubusercontent.com/.well-known/jwks`, and checks `iss`, `aud`, `exp`/`nbf`, `repository_owner == robotmoney`, `environment == --environment` and `sub == repo:OWNER/REPO:environment:NAME`. The result is a few named claims (`run.actions_proof`, `confirm.environment` log lines), never the token. `GITHUB_ACTIONS=true` without the request token, a token that does not verify, or a token for another Environment is `FLOOR` (exit 4) before any signer, and again at every broadcast (`confirmStage`). Off 8453 nothing changes.
- `src/counts.ts`: `deployments/frozen-counts/<sha>.json`. A missing SHA fails with `COUNTS_MISSING` and the message starts `FROZEN_COUNTS_MISSING`. No counts file is committed here until a Twin chain rehearsal has measured one.
  - `publish contracts --measure` (`bun src/cli.ts --measure ...`, Twin chain 918453 only, refused on 8453 by the floors) runs the deployer stages without frozen counts, learns each stage's transaction count from the broadcast, and writes `deployments/frozen-counts/<sha>.json` once every deployer stage is done. A reviewer reads the file, then commits it. A frozen file is never rewritten with different counts. Every later run, the plan job and the nonce check read that file and nothing else.
- `src/release-gate.ts`, `src/release-tag.ts`: the contracts-freeze gate of `--stage plan` on 8453 (core 1524), and since issue 1816 of every non-dry run on 8453 that broadcasts (`releaseGated` in `src/cli.ts`: `publish`, `govern`, `--stage prove-control`, `--stage deploy`, `all`, the default run: any stage set but a `verify`-only one). A dry run, a `verify`-only run, `pause-all`, `record-receipt` and the Twin chain are never gated. ## The consensus receipt submitter is a Safe (issues 1750 and 1888)

**Deployed release (v0.5.0).** v0.5.0 registered the submitter with `register-committee` (a gateway batch plus a private commit, reveal and hand-over) and recorded through `RobotMoneyGateway.consensusRecordReceipt`. Both are gone. `src/committee-register.ts` keeps only what `evidence-check` needs to decode the historical `committee_registrations` entries of pinned releases and rehearsal fixtures.

Owner decisions 2026-10-10, 2026-10-19 and 2026-10-20: no single key anchors a consensus receipt, on any chain, in any mode (production 8453, rehearsal 8453, Twin). The submitter is a SafeL2 1.4.1 Safe (a multisig, threshold 2 or more) that holds `RECEIPT_SUBMITTER_ROLE` on the receipt contract and nothing else. It MAY be the governing Safe, and its owners may be shared with it. `src/submitter-safe.ts` pins what it must be: the canonical SafeProxy 1.4.1 code hash, the SafeL2 singleton, `VERSION` 1.4.1, threshold at least 2, no module, no guard, the canonical fallback handler, and never the timelock, admin (= the deployer), the pauser or the emergency address (also not as an owner: role separation).

- `govern --row register-submitter --submitter 0x<Safe>` (`src/submitter-register.ts`) schedules exactly ONE delayed timelock call, `ConsensusRecommendationReceipt.grantRole(RECEIPT_SUBMITTER_ROLE, safe)`, on every chain and kind. These pre-checks run BEFORE the timelock round is scheduled, so a refused submitter spends no delay: the submitter is a canonical Safe (a key, no code, is refused), the timelock holds the admin role of `RECEIPT_SUBMITTER_ROLE` on the receipt, and the Safe does not hold the role yet. The read-back is `hasRole(RECEIPT_SUBMITTER_ROLE, safe)`. The evidence entry is `submitter_registrations` (the `submitter_safe` facts, the schedule and execute transactions). There is no `--agent-label`, no private half and no batch.
- `govern --row release-receipt` is refused once RouterGovernance holds `RECEIPT_RELEASER_ROLE` (or still holds `ADMIN_ROLE` on an unmigrated proxy): the timelock cannot release directly, a release alone would burn the receipt, and the message names `--row apply-receipt`. `apply-receipt` is unchanged.
- `record-receipt --submitter 0x<Safe> --signer <gas payer> --owner-signer ... --payload FILE --receipt-id ID --payload-digest D --payload-uri URL` records DIRECTLY on the receipt contract (`recordReceipt(bytes32,bytes32,string)`, the Safe is `msg.sender`). The served payload bytes are mandatory: the verb recomputes the domain-separated digest (`keccak256("robotmoney:consensus-receipt:v1\n" + compact JSON + "\n")`) and the receipt id (`keccak256("robotmoney:consensus-receipt-id:v1\n" + session_id + "\n" + subject_id)`) and refuses a different `--payload-digest` or `--receipt-id`. A missing Safe, an EOA, a missing, unsupported (`schema_version` other than 1.0) or malformed payload, a wrong id or digest, a Safe that is not canonical and an absent live `RECEIPT_SUBMITTER_ROLE` all fail BEFORE any signer is constructed (no passphrase prompt, no send), at the CLI and in `recordReceipt` itself (the signers are passed as factories). The operator first verifies the analyst signatures with `rmpc receipt verify` on the same bytes. After the send it requires the Safe's `ExecutionSuccess`, the receipt contract's `ReceiptRecorded` and a read-back of id, digest, uri and submitter. An exact rerun sends nothing. A conflicting record fails. The evidence entry in `recorded_receipts` carries `submitter_safe` (threshold, owners, code hash, Safe transaction hash, nonce, signers).
- Rehearsal roles: the old governance Safe `0x5E68a40648DD23065b21b1C414e1178ddE6482ca` is the PROPOSER (the submitter Safe that records receipts); the new governing Safe (`SAFE_SALT_NONCE` 2026101002) is the APPROVER (registers the proposer and applies the receipt). The owner EOAs must differ from the sheet's ADMIN, PAUSER and EMERGENCY addresses or registration is refused, naming the owner.

- `evidence-check` refuses a submitter without `submitter_safe` in every mode, the timelock or the deployer as submitter, a registration that is not exactly one `grantRole(RECEIPT_SUBMITTER_ROLE, submitter)` on the receipt contract (the retired two-call batch included), a standalone `receipt_releases` entry in an evidence that sets `consensus_receipt.governance_has_release_role` (copy of the timelock manifest's `roles.governance_has_receipt_release_role`), and (with `--rpc`) a record the Safe did not execute or that the receipt contract did not log as `ReceiptRecorded`. ## Verify and govern

- verify (`src/verify-stage.ts`) calls the verifier in `src/verify`. Expected assets come from core's `config/protocol-assets.json`, `config/rwa-assets.json` and `config/agent-token-shortlist.json` (`poolFee` is the swap fee, the adapter comes from the vault manifest). It also checks the rmUSDC seed shares (the deployer holds none, the seed share receiver holds them) and that the token at the USDC constant has the pinned FiatTokenProxy code hash. On 8453 it also checks Blockscout and Sourcify.
- **The verify RPC needs no archive node (issue 1851).** Every log scan of the verifier (the per-vault KEEPER, EMERGENCY and allowlist scans, the two gateway agent scans, the deployer-role scan, the role-holder scan of every governed contract and the timelock-holder scan) starts at the run manifest's `firstBlock`. Each scanned contract's creation block is read from the receipt of the run's own deploy transaction (`eth_getTransactionReceipt` on every hash in `stages[].txHashes` and `vault_redeploys[].deploy_tx_hashes`): a CREATE receipt names the contract as `contractAddress`, and the CREATE2 factory call of the timelock stage carries the timelock's constructor logs. The verifier never reads state at a past block, so a pruned or public RPC such as `https://mainnet.base.org` serves it. **The verify RPC must serve `eth_getTransactionReceipt` for every deploy transaction of the run, and `eth_getLogs` from `firstBlock` to the head.** **An adopted timelock (issue 1835) is accepted.** When the timelock stage adopted a TimelockController someone else deployed at the predicted CREATE2 address, the run sent no creation transaction for it. The run manifest's adopted stages (`adoption.libraries[].address`) name it, and the verifier reads its earliest `RoleGranted` log from `firstBlock` on: it must be the TimelockController constructor's own grant, `RoleGranted(DEFAULT_ADMIN_ROLE, account = the timelock, sender = the CREATE2 factory)`, in a successful transaction (issue 1864). Only a constructor running under the factory emits that log, so the factory created this timelock at or after `firstBlock`, however the factory was reached (a direct call, a multicall, a smart account or a Safe). Anything else fails the timelock's scans, including a direct factory call whose earliest log is another grant. A scan label fails when the scan start is after a scanned contract's receipt block ("from-block N is after the vault's creation"), or when the run neither created nor adopted the contract (its history cannot be proven complete). A receipt or log read the RPC refuses fails the scan labels with a detail that starts `RPC_REFUSED`. A recorded deploy transaction the RPC returns no receipt for (issue 1864) is `RPC_REFUSED` only when the same RPC serves none of the run's other receipts and `eth_getTransactionByHash` does not know it either (a node that does not index old transactions). When the RPC serves them, the transaction is truly missing from the chain (an edited run manifest, a dropped transaction): the scan labels fail with a detail naming it, verify exits 13 and pauses all four vaults. When every failed label is such a read, verify exits `RPC_REFUSED` (30) and pauses nothing: an RPC without the data is not an incident. **Exit 30 means the deployment is NOT verified**: those scans did not run, so do not proceed to govern until verify passes. Any other failure still exits 13 and pauses all four vaults. Rerun verify against an RPC that serves the receipts. The upgradeability scans (the `UpgradesFrozen` and timelock `CallScheduled` reads, issue 1842) carry no proof of their own: they read the same proxies and the same timelock from the same `firstBlock`, whose creation the role scans prove in the same run. The standalone verifier takes the hashes with `--run-manifest <publish-run.json>`; without it a `--from-block` above zero fails every scan label.
- **verify on 8453 runs before govern and after it (issue 1667).** The order is publish, verify, govern, verify. `mainnetGovernMode` (`src/verify-stage.ts`) reads the CURRENT round of each unpause row in the run manifest: no unpause row scheduled is **pre-govern** (all four vaults must read `depositsPaused` true: rmUSDC pauses right after its seed deposit, core 1710), all four rows executed is **post-govern** (all four must read false). The manifest only picks the mode: `runVerifyStage` then reads `depositsPaused()` of all four vaults from the chain itself and adds a failed check on any disagreement, so an edited or stale manifest fails closed (exit 13 and `pause-all`). Anything between is **part-way** (some but not all of the four rows scheduled or executed): verify throws `GOVERN_PENDING` (exit 15) before it checks anything, names the govern command in the message and `details.next_command`, and the CLI does NOT run `pause-all` for it. The Twin chain reads the expected unpaused set from the manifest as before (`unpausedByGovern`), and `twin-publish.ts` runs verify, govern, verify (the second verify only when both `verify` and `govern` are on).
- **`govern --row apply-receipt` (issue 1696, issue 1698).** The Safe, through the timelock, applies one recorded consensus receipt as ONE `schedule` of one call: `RouterGovernance.applyReceipt(receiptId, payloadDigest, vaults, bps)`, gated by `RouterGovernance`'s `WEIGHT_SETTER_ROLE` (held by the timelock). The contract checks the receipt is recorded, unreleased and that `payloadDigest` equals the stored digest, then releases the receipt and sets the router's ACTIVE vector in the same call. The default vector is untouched and stays the fallback. Arguments: `--row apply-receipt --receipt-id 0x<bytes32> --payload FILE`. Refusals, all `USAGE` (exit 2) with nothing sent: the receipt is not recorded or is already released; the receipt digest of the payload bytes (`keccak256` of `robotmoney:consensus-receipt:v1\n` plus the bytes, `src/receipt-digest.ts`, issue 1754) differs from the digest the receipt stored; the weights do not sum to 10000 bps; the vector is not exactly the registry's router-eligible vaults (a missing vault, an ineligible vault carrying weight, an unknown or repeated bucket); the payload order is irrelevant, the vector is arranged in registry order. An active vector already in effect does not block the row: `applyReceipt` overwrites it. After the real delay the Safe executes the call and the tool reads `isReleased`, the router's active weights, its EFFECTIVE weights (`getEffectiveWeights()`, what deposits route by) and `votedWeightsActive()` back: the receipt must be released, `votedWeightsActive()` true and the active and effective weights equal to the receipt vector (`GOVERN` on any difference). On demand only: the row is not in `GOVERN_ROWS`, so stage 13 on 8453 stays the four unpauses (unpause-USDC, PROTO, AGENT, RWA) and no default run, stage run or numbered `--row` reaches it; on 8453 it runs only when named, with its own 172800 s delay (the first run exits `GOVERN_PENDING` with the resume command). The entry's `target` is the governance contract and it records the `payload_digest`, `voted_weights_active: true` and `effective_vaults` / `effective_bps`; `evidence-check` requires them. The verifier label `receipt: applied receipt is released and its weights are on the router` reads the last applied receipt back. On 8453 verify does not trust the run manifest's `receipt_applications` (issue 1701): every entry must be backed by its timelock batch on chain (the same check as `evidence-check --receipt-applications --rpc`: the schedule and execute transactions, the one `applyReceipt` calldata of the recorded vector, the delay), or verify fails (exit 13), so a forged entry cannot hide router weight drift. `evidence-check --delay-floor` is refused (exit 2) below the 8453 floor of the deployment kind (172800 s for production) when `--rpc` reads chain 8453. It does not mean one wait per operation. A run schedules one timelock operation per unpause the sheet asks for (`GOVERN_UNPAUSE_VAULTS` among USDC, PROTO, AGENT, RWA; chain 8453 requires all four), each its own Safe transaction, **all in one sitting**, and waits **one** 48 hour delay. On 8453 it then exits 15 (`GOVERN_PENDING`) once, with the ready time (the latest of the operations) and the exact next command. The same command resumes: it executes each operation after the delay and reads `depositsPaused() == false` back. An operation declared dependent on another (`GovernOpts.dependsOn`, none by default) carries that operation's id as the timelock `predecessor` and is executed in the same resume, never after a second wait. Deposits open on day 2. `update-delay` (an `updateDelay` round), `batch` (one `scheduleBatch` round that changes nothing) and `cancel` (a schedule, then a cancel) are demonstrations of the Safe tool: they run on a Twin fork after the unpauses, and are refused with USAGE on 8453. Which vaults unpause is sheet data; a vault the sheet does not list is recorded as skipped and stays paused. The run manifest keeps `scheduled`, `executed` or `cancelled` per row, so a half-done run resumes at its next phase (an operation already on the timelock is adopted, never scheduled twice). On 8453 there is no warp: the wait never blocks for more than an hour. On a Twin fork (eth_chainId is not 8453 and the RPC answers `anvil_nodeInfo`) the wait is warped instead, ONCE for all the unpauses: `evm_increaseTime` plus `evm_mine` (`src/rehearsal/twin.ts`), so the real 48 hour delay passes in seconds. The warp never runs on an RPC that answers 8453. Each warp moves the clock to one second past the latest ready time, no further, and logs the structured event `govern.warped` with `seconds`. The timelock's delay is never shortened: the fork enforces its real delay, and the warp only passes it. On a non-anvil RPC the run keeps waiting up to `--max-wait`, then exits `GOVERN_PENDING`. Pause semantics are not decided here: `unpause-*` rows send the `unpauseDeposits` call and read `depositsPaused()` back.

## CLI contract

**Verbs** (the optional first word; a verb and `--stage` are never combined, usage error 2):

| Verb | Runs | Resume |
|---|---|---|

## Rehearsal helpers (`src/rehearsal`, devops issue 56)
One Bun TypeScript CLI that runs every contract deploy (devops issue 61). This file documents `src/rehearsal/`, the rehearsal helpers (S7, devops issue 56). A rehearsal is the same runbook as production with different arguments, run on the Twin chain (918453). No mock Safe, no scripted Safe.

```
cd publish-contracts && bun install
bun run rehearsal keys --dir /dev/shm/rh/keys --password-file /dev/shm/rh/pw --chain-id 918453   # or omit --password-file for a hidden prompt (the passphrase stays in memory, no file)
bun run rehearsal args --rpc http://127.0.0.1:8545 --deploy-sha <core sha>                              # the publish-contracts argument set
bun run rehearsal fund-gas  --rpc http://127.0.0.1:8545 --sheet rehearsal/sheet.env                  # Twin fork: anvil_setBalance
bun run rehearsal fund-usdc --rpc http://127.0.0.1:8545 --sheet rehearsal/sheet.env --usdc-units 1000000   # Twin fork: the real FiatToken balance slot
bun run rehearsal warp --rpc http://127.0.0.1:8545 --seconds 172801                                  # Twin fork: move time forward
bun run rehearsal run --rpc http://127.0.0.1:8545 --dir /dev/shm/rh/keys --password-file /dev/shm/rh/pw --sheet rehearsal/sheet.env
```

- **keys** wraps `src/keystore/keygen.ts` (a Foundry keystore v3 writer in this package). It writes ENCRYPTED Foundry keystores (DEPLOYER, PAUSER, EMERGENCY, SAFE_OWNER_A/B/C) to a 0700 directory, each 0600, under one passphrase of 16+ characters. The passphrase comes from a 0600 file (the unattended CI path) or a hidden prompt, never an argument. On the hidden-prompt path the passphrase stays in memory: no passphrase file is written, and it is not printed, logged or put in the environment. For the mainnet test make the keys with `bun run rehearsal keys --dir <backed-up folder> --chain-id 8453` (no `--password-file`): `--chain-id 8453` sets `CHAIN_ID` in the fragment. The helper makes no voter keys and has no `--voters` flag: there is no voting (issue 1698). The seed receiver is Safe owner A's address (the tool makes no separate seed key). Keys made from the `release/v0.4.0-base` tag (older code) also wrote the passphrase to a plaintext 0600 file `<dir>.pw` beside the folder: run `shred -u <dir>.pw` after use and never back it up. The file sits BESIDE the keys folder, so a backup of the parent directory includes it: check backups for it and shred it before backing up the parent. `rehearsal run` still requires `--password-file`: the owner creates their own 0600 file on tmpfs and runs `shred -u` on it after use. The run-day steps are in `docs/operations/contract-release-runbooks.md` (section 4.3). It prints a sheet fragment (`ADMIN_ADDRESS`, `RECEIPT_ADMIN_ADDRESS`, `PAUSER_ADDRESS`, `EMERGENCY_ADDRESS`, `SAFE_OWNERS`, `SAFE_THRESHOLD`) of addresses and numbers only. It validates every name before it writes any key. Use a memory-backed directory.
- **fund-gas**, **fund-usdc** and **warp** (`src/rehearsal/twin.ts`) are the environment steps that may differ from production on a Twin fork. Each refuses unless the RPC is not chain 8453 and answers `anvil_nodeInfo`. `fund-gas` sets the balance of the deployer, pauser, emergency key and Safe owners of the sheet (`anvil_setBalance`) to `--wei`, default `TWIN_GAS_WEI` (2 ETH; the runner pre-flight needs 3x the simulated cost plus the L1 allowance, and 0.02 ETH was too thin). `fund-usdc` sets the deployer's real FiatToken balance by writing its balance storage slot (slot 9, `balanceAndBlacklistStates`), after it checks the token code hash against the pinned FiatTokenProxy, and reads the balance back. `warp` moves chain time (`evm_increaseTime`, `evm_mine`). Nothing else about the forked state is patched. Requests retry with backoff on HTTP 429. No secret is involved.
- **Mainnet test deposits (owner standing rule, 2026-10-09: every mainnet rehearsal and test uses 1 USDC).** The seed is 1 USDC (`SEED_DEPOSIT_USDC=1000000`, which the deploy only requires to be non-zero) and the test is one 1 USDC deposit into each of the four vaults, then a full redeem, from the deployer after the handover. No code enforces the amount. The deployer needs 5 USDC. The Twin sheet sets the caps at 1000 USDC TVL and 100 USDC per deposit for all four vaults, with no minimum. Those are Twin values only: the 8453 frozen sheet governs the real caps, so check its `tvlCap` and `perDepositCap` before the run. The 1 USDC test deposit is far below either. The casts are `deposit(uint256,address)`, `redeem(uint256,address,address)`, `redeemInKind(uint256,address,address)` on the vault and `record()` and `isFresh()` on the recorder (full list in `docs/operations/contract-release-runbooks.md`, section 4.3). rmAGENT needs a fresh recorder: `record()` and `isFresh()` immediately before the deposit (else `StaleRecorder(uint32,uint32)`, selector `0x4512c7f1`, once more than 1800 s have passed), redeem within 30 minutes of the last `record()` or poke again, and use `redeemInKind` if the USDC redeem reverts `StaleRecorder`. Twin-measured round-trip losses (expectations, not guarantees for mainnet): rmUSDC about 0, rmPROTO about 19 bps, rmRWA about 10 bps, rmAGENT about 592 bps.
- **fund** is the funder-persona path for a real chain (no Twin run uses it). It replaces the old shell funding script. The funder keystore arrives from the caller's credential tool in CHAIN_FUNDER_KEYSTORE and CHAIN_FUNDER_PASSWORD, is staged in a 0700 memory-backed directory and shredded on every exit. It refuses a wrong chain id, a duplicate recipient, the funder as a recipient, a contract recipient, a funder balance below total plus gas reserve, and plaintext signing env against a non-loopback RPC. Idempotent: a re-run sends only what is missing.
- **sweep** returns leftover ETH (and optional USDC) from every throwaway key to the funder. `run` calls it in a `finally` and on SIGINT, SIGTERM and SIGHUP, so it runs on every exit path.
- **run** reads the chain id from the RPC, refuses anything but 918453, refuses a sheet whose `CHAIN_ID` differs, calls the publish-contracts CLI with `rehearsalArgs`, then sweeps. On a Twin fork there is no funder (anvil funded the keys), so the sweep is skipped.
- **rehearsalArgs(chainId, rpc, opts)** returns `--chain-id --rpc --sheet --signer --environment --deploy-sha`. `publishArgs` builds production's set through the same function, so the two differ only in values (tested by `differingFlags`).

## Evidence check

`bun src/evidence-check.ts --evidence evidence/<run>/evidence.json --frozen deployments/frozen-counts/<sha>.json --deploy-sha <sha> [--rpc URL]`. Without `--rpc` it checks the recorded shape only. With `--rpc` (chain 8453) it reads the chain: deployer nonce equals the summed frozen counts, every receipt has status 1, `registry.listVaults()` equals the recorded manifests, and each govern entry shows CallScheduled and CallExecuted on the timelock with a block gap of at least 172800 s. On 8453 the govern evidence is the four vault unpauses (`GOVERN_STEPS`: `unpause-USDC`, `unpause-PROTO`, `unpause-AGENT`, `unpause-RWA`), all required (issue 1710: every vault deploys paused). Each step may repeat as a numbered `round` (1 to n, in order, each scheduled after the previous one executed, each with its own transactions and operation id). Every unpause round must be exactly one call on the chain: `unpauseDeposits()` on that step's own vault, so any other call on rmUSDC is rejected. Any other operation scheduled on 8453 (`update-delay`, `batch`, `cancel`, or anything else) is rejected. Per operation, the check expects one schedule transaction and one execute transaction at least 172800 s apart, with distinct timelock operation ids: no two entries may share a schedule or an execute transaction or an operation id. The unpauses are scheduled in one sitting, so there is no ordering rule between them. The template is `evidence.example.json`.

Governed proxies (issue 1809): when core's stage table lists `proxies`, the evidence must carry `upgrade_mode` (`upgradeable` or `frozen`) and a `proxies` entry per proxy name, copied from the verify stage record: `proxy`, `implementation`, `implementation_code_hash`, `authority` (the timelock), `mode`, `frozen`, `admin_slot_empty` and `beacon_slot_empty` (both must be true). Every vault address must be its proxy, and a proxy may read frozen only in `frozen` mode or after a `proxy_freezes` entry. A `layout_hash` recorded at deploy must equal its `checkout_layout_hash`. An `immutability_claim` is refused while any proxy reads upgradeable, and without the record's `immutability.still_mutable` list (ADR-0014 §5). The `proxy_upgrades` and `proxy_freezes` entries are checked like every other operation: both transactions status 1, at least the delay apart, none shared, on the recorded timelock. These checks read the record. With `--rpc` (or a recorded `--chain-fixture`) every `proxies` entry is also read from the chain (`upgradeabilityOnChainProblems` in `src/evidence-upgradeability.ts`, QA plan v1 L1): the ERC-1967 implementation slot names the recorded implementation, the admin and beacon slots are empty, the implementation's code hashes to `implementation_code_hash`, `upgradeAuthority()` is the evidence timelock, `upgradesFrozen()` is the recorded `frozen`, the proxy is initialized and the implementation's initializers are locked. The fixture keeps those storage words as decimal strings under `storage`, so the secret scan stays clean.

Recorded-fixture mode: `--chain-fixture FILE` (with `--frozen` and `--deploy-sha`, and no `--rpc`) runs the same chain checks over a fixture of what the chain returned. Record the fixture once, at the end of the run: `... --rpc URL --record-chain-fixture evidence/<run>/chain-fixture.json` (written only when every check passed). The `evidence` job in `ci.yml` checks every `evidence/*/evidence.json` this way, so acceptance criteria 2 (nonce and per-stage counts) and 3 (receipts and the 172800 s gap) run offline in CI. A run with no frozen file or no `chain-fixture.json` fails that job. A read the fixture lacks is an error. The check also links the unpause govern rows to the `depositsPaused()` reads: a basket vault reads `depositsPaused() == false` exactly when the latest round of its `unpause-<VAULT>` step has an executed receipt, and rmUSDC always reads false. After govern, the verify stage applies the same link: a vault the unpause row unpaused is expected `depositsPaused=false`, every other basket and agent vault is expected `depositsPaused=true` (`unpausedByGovern` in `src/verify-stage.ts`).

Secret scan: `--evidence` also scans every file of the run folder for key material (`scanEvidenceFolder`; `src/ci/scan-rehearsal-secrets.ts` runs the same scan over a rehearsal's evidence). A 64-hex value is flagged unless it sits in a public hash field, judged value by value, never by its line (QA plan v1 E8, issue 1689): a 0x bytes32 right after a label that names a hash (`tx`, `hash`, `transaction`, `block`, `salt`, `digest`: `"txHash": "0x…"`, `"tx_hashes": ["0x…"]`, `Hash: 0x…`), a pretty-printed JSON line holding one 0x bytes32 value or list element under a public name, `sha256:<64 hex>` directly under `configHashes` / `config_hashes` (the isomorphism report), and the frozen counts anchor `crossChecked.fileHash`. A public name is an allowlist, never "any name but a secret one": a hash word, an owned id (`operation_id`, `receipt_id`, `pool_id`, never a bare `id`), `predecessor`, a role or an event topic; any non-secret key directly inside a hash-named object (`"code_hashes": {`); and the `data` of an event log. Every other name exempts nothing (`"signer": "0x…",` is flagged), and a name with a secret or credential word (`private`, `key`, `secret`, `seed`, `mnemonic`, `password`, `token`, `auth`, `credential`, `bearer`, `session`) never exempts, so `"privateKey": "0x…",` and `"token": "0x…",` are flagged; so is a bare 64-hex anywhere else, and a key beside a tx hash, even on a line that says `hash` or `tx`. The public timelock shapes of issue 1759 (`apply-receipt-0x…`, the operation ids of `govern.waiting` and `timelock.effect` log lines) stay allowed. `privateKey: …`, `"private_key": "…"`, `"authToken": "…"`, `"credential": "…"`, `"bearer": "…"` and `"token": "…"` count as a secret assignment, like `PRIVATE_KEY=…`; a `token` whose value is a 20-byte address (an ERC-20 in the asset configs) does not.

No workflow runs a read-only mainnet verify. `tests/chain-dependent-s8-s13.test.ts` runs the verifier against chain 8453 only when `deployments/8453/verify-inputs.json` (`sheet_json`, `frozen`, `deploy_sha`, `from_block`, `artifacts`, optional `run_manifest`) and `MAINNET_RPC_URL` are present, and skips with the reason otherwise. No such inputs file is committed.

**Twin upgrade lifecycle rehearsal (issue 1811).** (`src/ci/twin-upgrade-lifecycle.ts`, `src/upgrade-lifecycle.ts`). After `twin-publish` with `sheet-overlay: deployments/twin-918453/upgrade-rehearsal.env` (`UPGRADE_MODE=upgradeable`), the script deploys a second copy of the build's gateway implementation with `deploy-implementation --proxy gateway` (issue 1861; it also checks that a rerun reuses the entry), upgrades the gateway proxy to it with `govern --row upgrade-proxy`, schedules the freeze of every core proxy in one batch bound to `upgradeability.json` with `govern --row freeze-upgrades --no-warp --max-wait 0`, queues a second upgrade before the freeze executes, executes the freeze with the same row, and shows the queued upgrade is refused after the freeze. It checks the run manifest's `proxy_upgrades` and `upgrade_freezes` as `evidence-check` does.
